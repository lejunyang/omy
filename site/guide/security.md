# 安全边界

::: danger 先读这一页再决定怎么用
任何加密工具都有能力边界。把它用在设计目标之外的场景，会得到虚假的安全感。
:::

## 威胁模型：防什么

| 场景 | 防护手段 |
|---|---|
| 设备丢失或被盗 | 静态数据全量 AEAD 加密 |
| 云盘运营商或同步服务方可访问文件 | 只上传密文，密钥永不出本机 |
| 共享设备上其他人随手翻看 | 文件名加密 + 密码解锁 |
| 攻击者拷走密文离线爆破 | Argon2id 内存硬 KDF |
| 攻击者篡改密文让你解出被污染的内容 | AEAD 认证 + 文件头 MAC |
| 重排、截断、跨文件移植密文块 | nonce 绑定块序号，AAD 绑定文件 UUID，末块带 final 标记 |
| 篡改文件头把 KDF 参数改弱以便爆破 | 文件头 MAC 覆盖全部参数 |
| 同一 WiFi 下嗅探传输内容 | 端到端加密信道，且只传密文 |

## 明确不防什么

::: warning 以下场景请不要依赖 omy
:::

**隐藏「这是个加密文件」这件事。** 文件头有明显的 magic（`OMYFILE`）。伪装后缀只能挡住随手点开，`binwalk` 之类的工具一眼看穿。omy 接受「文件可被识别为加密文件」这个前提。

**专业数字取证。** 内存取证、冷启动攻击、SSD 残留数据恢复都不在防护范围。

**国家级定向攻击。** 这需要的是一整套操作安全体系，软件层面解决不了。

**设备已被植入恶意软件。** 键盘记录器直接就能拿到密码。被 root 的系统上任何本地加密都没有意义。

**胁迫（rubber-hose）。** 密钥槽的不可探测性提供**有限**帮助——旁人无法判断文件配了几个密码——但不能对抗持续的物理胁迫。

**完全隐藏元数据。** 文件大小、数量、修改时间默认可见。

**已解锁状态下的截屏录屏。** 内容一旦显示在屏幕上就无法控制。

**SSD 上的安全擦除。** wear leveling 与 TRIM 让覆写擦除在物理层面不可靠，所以 omy **不提供**「安全删除」这种功能——提供一个做不到的承诺比不提供更糟。

## 信任边界

```
受信任
├── 用户的密码（假定用户自己保管妥当）
├── 运行 omy 的操作系统内核
├── OS 密钥库（Keychain / Keystore / TPM）
└── omy 主进程（持有密钥的唯一进程）

半受信任（隔离运行）
└── FFmpeg 子进程 —— 降权 + 不持有任何密钥

不受信任
├── 磁盘上的密文文件（假定攻击者可完整获取）
├── 云同步服务
├── 局域网（假定可被嗅探）
├── 待加密的输入文件（可能是恶意构造的）
└── 局域网对端设备（只给密文，不给密钥）
```

FFmpeg 处理的是不可信输入（任意媒体文件是常见的攻击面），因此**只在独立子进程里运行，通过管道通信，不接触任何密钥**。即使它被输入文件攻破，也拿不到密钥。

## 命令行参数是旁路

这是 CLI 上优先级最高的一条：**命令行参数对同机其他用户可见**（`ps aux`、`/proc/*/cmdline`、任务管理器），并且会进入 shell 历史文件。

所以 omy **不提供** `--password <明文>` 参数。可用的输入方式见[密码与密钥槽](/guide/passwords#密码怎么输入)。

## 明文不落盘

预览与播放走自定义协议 `omystream://`，按需解密内存中的块，不写临时文件。

这条性质有前置条件，是实测得出的：响应头必须带 `Cache-Control: no-store, no-cache, must-revalidate` 与 `Pragma: no-cache`，否则 WebView 可能把解密后的数据写进磁盘缓存。实现里这些头是必须的，不是可选优化。

另外界面**不启用** Tauri 的 `protocol-asset` 协议——它会直接暴露文件系统路径，与这个目标相悖。

## 已知的实现层面限制

`omy doctor` 会如实报告这些，不藏着：

**`--cipher xchacha20` 实际是 ChaCha20-Poly1305**（12 字节 nonce），不是 XChaCha20（24 字节 nonce）。安全性没问题，但与其他实现的 XChaCha20 不能互操作。

**SPAKE2 实现未经第三方审计**，且其作者自述可能不是常量时间。配对场景下可接受（PIN 一次性随机、用完即弃），但如果你的威胁模型包含本地时序侧信道，请自行评估。

**平台验证范围有限**：Windows、Android 与 macOS（Apple Silicon）已真机实测，Linux 与 macOS（Intel）尚未验证。

## 密码遗忘等于数据丢失

设计上不存在后门、主密钥或恢复短语。

这不是疏漏：任何找回机制都是一条绕过密码的路径，也就是攻击面。请自行备份密码。

## 高档位 KDF 的双向成本

KDF 参数写进文件头，解密时必须用同样的参数。用 `sensitive`（1 GiB 内存）加密的文件，在内存不足的设备上**打不开**。这不是 bug，是内存硬 KDF 的固有性质。
