# 08 · UI/UX 设计

> 设计目标（用户要求）：**简洁、美观、易用**。
>
> **配套可交互原型**：[appendix/ui-prototype.html](appendix/ui-prototype.html) —— 浏览器直接打开，可切换深/浅主题、网格/列表视图、锁定/解锁态，实际观察本文档描述的界面效果。
>
> 原型已通过 23 项自动化断言验证（含锁定态信息隐藏完整性、状态恢复正确性、主题切换、色值生效），全部通过。详见 §10。

## 1. 设计原则

| 原则 | 落地 |
|---|---|
| **加密应该是隐形的** | 解锁后，浏览体验与普通文件管理器无异——显示真实文件名、缩略图，双击即播放 |
| **状态永远清晰** | 锁定/解锁、本地/远程、播放路径、加密强度，任何时候都一眼可见 |
| **诚实高于美观** | 不隐藏局限（伪装强度、SSD 擦除、转码不可逆），宁可多一句警告 |
| **危险操作需要摩擦** | 删除原文件、转码、启用弱参数都要二次确认 |
| **默认值即最佳实践** | 用户不改任何设置也应得到安全合理的结果 |

### 5.2 错误提示原则

**说明发生了什么 + 为什么 + 能做什么**，不只报错误码。

| 场景 | 提示 |
|---|---|
| 密码错误 | 「密码不正确，或此文件不属于当前密码」 + [尝试其他密码] |
| 版本过新 | 「此文件由更新版本的 CryptoVault 创建」 + [检查更新] |
| header 损坏 | 「文件头已损坏或被篡改」 + [尝试从分片恢复] |

| 格式不支持 | 「此视频格式无法在应用内播放」 + [用外部应用打开] |

## 6. 危险操作的摩擦设计

| 操作 | 摩擦级别 | 设计 |

## 7. 多语言（决策 D-29：简中 + 英文）

### 7.1 语言检测顺序

```
1. 用户手动设置（持久化）
2. 系统语言
   - 桌面：OS locale
   - Android：Locale.getDefault()
   - iOS：Locale.preferredLanguages
3. 英语兜底
```

支持区域变体回退：`zh-TW` → `zh-Hant` → `zh` → `en`。

### 7.2 技术方案

| 层 | 方案 |
|---|---|
| 前端 | `i18next` + `react-i18next`（或等价） |
| Rust 后端 | `rust-i18n` —— **错误消息也必须翻译** |
| 文案文件 | `locales/{zh-CN,en}/{common,errors,settings}.json` |

**关键**：Rust 返回给前端的应该是**错误码 + 参数**，而非拼好的中文字符串：

```rust
// ❌ 后端拼字符串
Err("密码不正确".into())

// ✅ 结构化错误，前端翻译
Err(AppError::WrongPassword { tried_slots: 8 })
```

### 7.3 文案文件结构

```json
// locales/zh-CN/common.json
{
  "app": { "name": "CryptoVault" },
  "unlock": {
    "title": "解锁",
    "password_placeholder": "密码",
    "biometric": "使用指纹解锁",
    "deriving_key": "正在派生密钥…",
    "scanning": "正在扫描… {{current}} / {{total}}"
  },
  "playback": {
    "tier_p1": "直通", "tier_p2": "转封装", "tier_p3": "全解码",
    "tier_p1_desc": "零处理，seek 最快"
  },
  "file_count": "{{count}} 个文件"
}
```

### 7.4 本地化注意点

| 项 | 处理 |
|---|---|
| **文件名排序** | ⚠️ **必须用 locale-aware 排序**，不能用字节序。中文按拼音（`zh-CN`）或笔画，需用 ICU collation |
| **数字/文件大小** | 千分位分隔符、小数点符号随 locale |
| **日期时间** | 中文「2026年8月29日」/ 英文「Aug 29, 2026」 |
| **复数** | 英文有单复数（1 file / 2 files），中文没有。用 i18next 的 plural 规则 |
| **文本膨胀** | 英文通常比中文长 30–50%，UI 布局需留弹性，避免固定宽度 |

### 7.5 RTL 预留（未来）

虽然首期不做阿拉伯语/希伯来语，但**布局要提前预留**，事后改代价很高：

```css
/* 用逻辑属性而非物理属性 */
margin-inline-start: 12px;   /* 而非 margin-left */
padding-inline-end: 8px;     /* 而非 padding-right */
text-align: start;           /* 而非 left */
```

并在根元素设置 `dir` 属性以便未来切换。

### 验证中发现并确认的两处设计要点

1. **锁定态的还原必须是"记忆式"而非"重设式"**
   断言「解锁后仅保留 2 个锁图案」专门用于捕捉一类真实缺陷：若锁定时直接覆写样式、解锁时统一重设为"正常"，那么**本来就因密码不匹配而锁定的文件会被错误地显示为已解锁**。原型采用进入锁定态前把原始状态存入 `data-*`、退出时逐项还原的方式，实测 12 项中恰好还原出 2 个应保持锁定的项。
   → 生产实现中，锁定态应当是**渲染层根据数据源重新渲染**，而不是对 DOM 做可逆的样式覆盖；每个文件的"是否已解锁"必须是数据字段，不能是视图状态。

2. **锁定态不能只隐藏文件名**
   缩略图（画面内容）、元信息（大小、时长、编码）同样是信息泄露。断言覆盖了全部三者。文件大小尤其容易被忽略——它在锁定态下应显示为「密码未解锁」而非真实字节数，否则配合文件数量仍可推断库内容规模。

### 验证方法说明

- 采用 iframe 载入原型并从父页面读取 `contentDocument` 实际 DOM，**通过与生成路径不同的方式回读**，而非检查源码字符串。
- `file://` 协议下 iframe 跨源受限，验证在本地 HTTP 服务（同源）下执行。
- 除自动化断言外，另在浏览器中以真实鼠标点击复核了「锁定态」「浅色主题」两个关键状态的视觉呈现。
