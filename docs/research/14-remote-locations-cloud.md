# 14. 远程位置：云盘接入

> 状态：**设计草案**，尚未实现。
> 本文覆盖首期远程位置形态「公有云盘」的接入方式、加密文件识别、
> 能力矩阵与 UI/交互设计。

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 怎么接 | 在 `omy-core` 抽 `RemoteStore` trait，新建 `omy-cloud` crate 放各家驱动 |
| **首期接哪个** | **WebDAV 优先**，光鸭云盘次之。理由见 §3 |
| 要不要接 Go SDK | **不接**，但 WebDAV 走现成 crate（`reqwest_dav`），不手写协议 |
| 怎么识别 omy 文件 | 复用现有「只读头部」性质：一次 Range 请求取前 480 B 即可判定 + 试解锁 |

| 密文缓存 | **磁盘缓存 + 可设上限**，默认 2 GiB，LRU 淘汰。只缓存密文，见 §8 |

## 1. 为什么现在能做，以及必须先解决什么

### 1.1 已有的地基

远程位置不是从零开始。项目里已经有两处关键预留：

- **`omy_core::source::BlockSource`** 已经定义了 `read_ct(offset, len)` +
  `is_remote()`。局域网共享（`omy-gui/src/remote.rs`）已经证明这条路走得通：
  **只拉头部就能识别文件、解出文件名和缩略图，载荷等播放器真要了再按需取。**
- **`omy-gui/src/remote.rs` + `RemoteScreen.vue`** 已经确立了「只读远端」的
  完整范式：平铺列表、无路径、不出现加密按钮、状态栏标只读。

云盘与局域网远端的**结构是同一个**：都是「别人家的字节，我只能按 offset 取」。
差别只在传输层（Noise over TCP vs HTTPS REST）和权限（对端授权 vs OAuth/令牌）。

### 1.2 必须先想清楚的三件事

**① 云盘没有 `rename` 原子性保证。**

`fsatomic.rs` 的五步流程（写 tmp → fsync → fsync 目录 → rename → fsync 目录）
建立在 POSIX/NTFS 的同文件系统 rename 原子语义上。云盘的「重命名」是一次
独立的 HTTP 调用，可能失败、可能超时后其实成功了。**照搬会得到一个假的
安全感**：代码长得像原子写，实际不是。

这与 `storage.rs` 里记下的 SAF 教训是同一类问题——当时的结论是「`content://`
rename 之后 URI 会变，恰好打掉原子写依赖的前提」，所以选了
MANAGE_EXTERNAL_STORAGE。云盘上没有这个逃生口，只能如实降级并明说。

**② 云盘的「目录」不是路径，是 ID。**

光鸭的 `parentId` 是整数 ID，不是路径字符串。`tree.rs`/`pack.rs` 的目录遍历
全部基于 `std::path`。远程位置**不能**复用它们，必须走独立的列举逻辑。

**③ 只读与可写必须由后端声明，不能由前端猜。**

这是本设计里唯一的强约束。理由在 §5.1。

## 2. 远程位置的分层设计

```
┌──────────────────────────────────────────────────────────┐
│ omy-gui                                                  │
│  places.rs      位置注册表（本地目录 / 云盘账号 / 局域网设备）│
│  cloud_cmds.rs  Tauri 命令层                              │
└───────────────┬──────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────┐
│ omy-cloud（新 crate，GPL-3.0，与 gui 同级）                 │
│  trait RemoteStore   列举 / 读 Range / 写 / 删 / 改名       │
│  Capabilities        能力位图 ← 唯一真相                    │
│  auth/               令牌存取与刷新                         │
│  drivers/guangya.rs  光鸭驱动（首期唯一）                    │
│  CloudSource         impl omy_core::source::BlockSource    │
└───────────────┬──────────────────────────────────────────┘
                │ 只依赖 BlockSource，不反向依赖 cloud
┌───────────────▼──────────────────────────────────────────┐
│ omy-core（MIT OR Apache-2.0，保持零网络依赖）                │
│  source::BlockSource   已存在，不改                         │
│  scan::probe_bytes()   新增：从字节切片判定，不碰文件系统      │
└──────────────────────────────────────────────────────────┘
```

### 2.1 为什么新开 crate 而不是塞进 omy-net

`omy-net` 是局域网协议栈（Noise IK、mDNS、SPAKE2 配对），它的依赖和威胁模型
与云盘完全不同：局域网是「我信任的对端设备」，云盘是「不可信的第三方托管」。
混在一起会让 `omy-net` 拖进 HTTP 客户端、OAuth、JSON 这一整套依赖，而这些
对局域网场景一点用没有。

许可证上也要分开：`omy-core` 必须保持 MIT/Apache 且零网络依赖（README 承诺
「零 FFmpeg 依赖」的同款理由——它要能被任何人集成）。云盘驱动带 HTTP 客户端，
放 `omy-cloud` 并定为 GPL-3.0，与 gui 一致。

### 2.2 `omy-core` 需要的唯一改动

新增一个纯字节判定函数，不碰文件系统：

```rust
// crates/omy-core/src/scan.rs

/// 从已读到的字节前缀判定是否为 omy 文件并尝试解锁。
///
/// 与 `probe_file` 的区别是**不碰文件系统**：远程位置拿到的是一段
/// HTTP Range 响应，既没有路径也没有 File 句柄。
///
/// `file_size` 由调用方给出（本地来自 metadata，云盘来自列目录响应），
/// 因为这个函数本身不应该知道字节是从哪来的。
///
/// 调用方需保证 `prefix` 至少有 `MIN_PROBE_SIZE`(480) 字节，
/// 否则返回 `Truncated` —— 这与「文件损坏」是两回事，见 MIN_PROBE_SIZE 文档。
pub fn probe_bytes(
    prefix: &[u8],
    file_size: u64,
    session: &SessionKeys,
) -> Result<Option<ProbeHit>>
```

**重构成本很低。** 现有 `probe_file` 的函数体里只有两处碰文件系统
（`read_header_bytes(path)` 取前缀、`std::fs::metadata(path)` 取大小），
其余全是对 `prefix` 切片的纯计算。

**返回类型要拆一层。** 现有 `ScanHit` 带 `path: PathBuf`，而云盘上的文件
没有路径（只有 `file_id`）。塞一个假路径进去会让上层拿它去 `std::fs::open`，
得到一个指不到真正原因的 NotFound。所以：

```rust
/// 与来源无关的识别结果。
pub struct ProbeHit {
    pub file_size: u64,
    pub header: FixedHeader,
    pub unlock: UnlockOutcome,
}

/// 本地扫描结果 = 识别结果 + 路径。
pub struct ScanHit {
    pub path: PathBuf,
    pub hit: ProbeHit,
}
```

`probe_file` 改为 `probe_bytes` 的薄封装（读 480 B + metadata 再转调），
避免两处实现漂移——这是 AGENTS.md 里「同一逻辑不允许两处实现」的要求。
`ScanHit` 是公开 API，拆分是破坏性变更，要同步改 `omy-cli` 与 `omy-gui` 的调用点。

**一处容易忽略的行为要保持一致：** `probe_file` 里用的是
`session.scannable_for()` 而非 `all_for()`——只拿 vault/device 类凭据，
portable/recovery 成本太高不参与扫描。云盘上更要守住这条：那里每个文件
还额外摊一次网络往返，用错凭据集合会让扫描慢到无法接受。

## 3. 接入策略：WebDAV 优先，私有 API 按需补

这一节回答两个问题：**先接什么**，以及**维护成本从哪来、怎么压住**。

### 3.0 结论：把远程位置分成两类，维护策略完全不同

| | 通用协议层 | 厂商私有 API 层 |
|---|---|---|
| 代表 | **WebDAV**（首期） | 光鸭、115、123 |
| 数量 | **1 个驱动** | 每家一个 |
| 协议是否会变 | 否，RFC 4918 冻结了二十年 | **会，且不通知** |
| 覆盖面 | NAS、Nextcloud、坚果云，以及所有被 AList / CD2 / LitePan 中转出来的云盘 | 一家一个 |
| 维护成本 | 一次写完基本不用动 | **持续跟进** |

**先做 WebDAV，用一个驱动换掉绝大部分覆盖面。** 这直接回答了维护顾虑：
私有 API 的维护成本不是「写的时候贵」，而是**「写完之后一直贵」**——
接口随时会调整，而且你不会收到通知，只会收到用户报障。WebDAV 没有这个问题。

一个具体的旁证：光鸭官方**不提供**原生 WebDAV，但社区已经用
LitePan / CloudDrive2 把它中转成 WebDAV 在用。也就是说，**omy 接一个 WebDAV
驱动，就顺带支持了光鸭**——只是多一个用户自建的中转层。

### 3.1 WebDAV 要不要自己写：不用

Rust 侧有现成且活跃的 crate：

| crate | 说明 |
|---|---|
| `reqwest_dav` | 基于 tokio + reqwest 的异步 WebDAV 客户端，覆盖 get / put / mv / cp / delete / mkcol / list，支持 Basic 与 Digest 认证 |

它与我们已经要引入的 `reqwest` 同源，不会多拖一套 HTTP 栈。

**而且 WebDAV 的读取根本不需要「WebDAV 客户端」。** 这是它最适合 omy 的地方：

- **列目录**用 `PROPFIND`（XML），这部分交给 `reqwest_dav`；
- **读文件就是普通的 HTTP GET**，`Range: bytes=a-b` 直接可用，
  是标准 HTTP 语义，与 `CloudSource` 的需求完全对齐。

也就是说，**流式播放这条最关键的链路，在 WebDAV 上是白送的**，
不需要像光鸭那样先换直链、还要处理直链过期。

### 3.2 但不要假设「标准协议就没有差异」

rclone 的 WebDAV 后端专门有一个 `vendor` 配置项，可选
`nextcloud` / `owncloud` / `sharepoint` / `sharepoint-ntlm` /
`infinitescale` / `fastmail` / `rclone` / `other`——**这本身就是证据**：
标准之上仍有一层现实差异。已知的几处：

- 原始 WebDAV **不支持修改时间和哈希**；Nextcloud / ownCloud / Fastmail
  靠 `X-OC-Mtime` 这类私有头补上。
- Nextcloud 有自己的分块上传（rclone 默认 10 MiB 一块）；
  ownCloud Infinite Scale 走 tus 协议。
- SharePoint 会改动上传文件的大小和哈希，导致无法用它们比对文件是否变化。
- 部分服务端在读取时会 302 跳到另一个域，标准客户端此时**会丢掉
  `Authorization` 头**（这是正确的安全行为），于是报 401。

**对 omy 的影响其实很小**，因为我们只需要「列目录 + Range 读 + 整文件写」
这个最小子集，用不到锁、属性、修改时间。但**必须把它当成有差异的协议来测**，
而不是写完一个 Nextcloud 能跑就宣布支持 WebDAV。

设计上照抄 rclone 的做法：留一个 `vendor` 字段，默认 `generic`，
差异点集中在一处而不是散落在调用点。

### 3.3 那光鸭这类私有 API 呢：不接 Go SDK，但也不急着自己写

调研中找到两个现成的光鸭客户端库：

| 库 | 语言 | 许可 | 能力 |
|---|---|---|---|
| `DDSRem-Dev/guangyaclient` | Python | MIT | 读写全套 |
| `gitee.com/hefy27/pan-client` 的 `guangyapan` 驱动 | Go | Apache-2.0 | 读写全套，含分片/断点续传 |

**不接 Go SDK，三条理由：**

**① 语言边界要么开进程要么开 FFI，两条路都糟。**
子进程方式意味着分发时多带一个二进制，Android/iOS 上根本走不通（应用不能
随意 fork 可执行文件）。cgo FFI 方式则要求 Go 侧编成 c-archive，交叉编译
矩阵从「5 个 Rust target」变成「5 × Go toolchain」，而本项目要覆盖
Windows/macOS/Linux/Android/iOS 五端。

**② 拖垮 MSRV 与构建可复现性。** Cargo.toml 里写得很清楚，RustCrypto
刻意固定在 0.10、MSRV 锁 1.85。引入 Go 工具链会让「clone 下来 cargo build
就能跑」这个性质消失。

**③ 引入 SDK 并不能免除维护成本，只是换了个人替你踩坑。**
这点要说清楚，因为它正是维护顾虑的核心：光鸭接口一变，Go SDK 也得跟着改，
你仍然要等它更新、要升级依赖、要重新验证。**语言边界带来的是额外成本，
不是省下的成本。**

**所以私有 API 的正确策略是「按需求驱动，而不是按可能性驱动」：**
WebDAV 做完之后，如果用户确实在用光鸭且嫌中转层麻烦，再补一个原生驱动
（那时它本身很薄——本质是 HTTP + 固定 header + REST，唯一特殊的是 GCID 哈希
和 OSS V1 签名，在 Rust 里各十几行，而 `sha1`/`hmac` 本来就在 workspace 里）。
**在此之前不写。** 过早接一家私有 API，等于凭空给自己加一份长期维护负担。

### 3.4 需要新增的 Rust 依赖

WebDAV（P1 必需）：

| 依赖 | 用途 | 说明 |
|---|---|---|
| `reqwest`（`rustls-tls`，禁 `default-features`） | HTTP | 不能带 native-tls，否则拖进 OpenSSL，交叉编译到 Android 会炸 |
| `reqwest_dav` | PROPFIND / MKCOL / MOVE 等 WebDAV 动词 | 与 `reqwest` 同源 |

私有云盘驱动（P3 及以后，真要做时才加）：

| 依赖 | 用途 |
|---|---|
| `sha1` | GCID 秒传哈希，RustCrypto 系，与现有 `sha2`/`hmac` 同源 |
| `base64` | OSS 签名 |
| `quick-xml` | OSS 分片上传的 XML 响应（仅两个字段，但手写易碎） |

`serde`/`serde_json`/`hmac`/`uuid`/`tokio` 已在 workspace 里，直接复用。

## 4. 光鸭云盘接入细节

### 4.1 认证：两条通道，能力完全不同

调研确认光鸭有三条第三方通道，与 omy 相关的是前两条：

| 通道 | 拿到什么 | 能力 | omy 的定位 |
|---|---|---|---|
| **A. 官方 OAuth / 扫码授权** | access_token + refresh_token | **只读**（列目录、下载直链） | 未来首选，但目前平台侧只放开只读 |
| **B. 短信验证码登录** | 同上，但走网页版内置 client_id | **完整读写** | 首期实现，用户自己的账号自己授权 |

这里有个必须向用户如实说明的现实：**官方授权通道目前只给只读**。
CloudDrive2 1.0.11 和 SmartStrm v0.4.19 的光鸭驱动都明确标注「受平台接口限制
仅只读」。要写入只能走 B。

所以 omy 的设计是：**两条通道都支持，并把差异如实反映到能力位图里**。
用户用 A 登录就得到只读位置，用 B 登录得到可写位置——而不是假装都能写，
等用户点了加密才报一个看不懂的错。

认证端点（`account.guangyapan.com`）：

```
POST /v1/shield/captcha/init          人机验证初始化
POST /v1/auth/verification            发送短信验证码
POST /v1/auth/verification/verify     校验验证码 → verification_token
POST /v1/auth/signin                  登录 → access_token + refresh_token
POST /v1/auth/token                   grant_type=refresh_token 刷新
POST /v1/user/me                      用户信息（校验令牌是否还活着）
```

业务端点（`api.guangyapan.com`）：

```
POST /userres/v1/file/get_file_list            列目录（parentId 为整数 ID）
POST /nd.bizuserres.s/v1/file/get_file_detail  文件详情
POST /nd.bizuserres.s/v1/get_res_download_url  取下载直链（302，带有效期）
POST /nd.bizuserres.s/v1/get_res_center_token  上传：取 OSS STS 凭证
POST /nd.bizuserres.s/v1/check_can_flash_upload  秒传判定（GCID）
POST /nd.bizuserres.s/v1/file/get_info_by_task_id 上传结果回执
POST /nd.bizuserres.s/v1/file/create_dir | rename | move_file | delete_file
```

### 4.2 令牌存哪里——这是个安全决策，不是工程细节

**令牌不能明文落盘。** 一个 refresh_token 等于用户整个云盘的长期访问权，
而 omy 的整个卖点是「文件在磁盘上是密文」。如果令牌是明文 JSON，
攻击者拿不到文件内容却能把用户的云盘搬空。

项目里已经有现成的答案：`omy-net` 的设备库就是**加密持久化**的
（PROGRESS.md 记为「加密持久化、授权会话」）。云盘令牌复用同一套机制，
不要另起一份。

配套的一条：**令牌绝不能进 WebView。** `remote.rs` 的
`remote_file_hides_internals` 测试已经立了规矩——handle 和 header 都
`#[serde(skip)]`。云盘的 token、OSS 临时密钥、下载直链同理，
前端只拿到 `place_id` 这种不透明标识。

### 4.3 识别云盘里的 omy 文件

这是整个设计里最舒服的部分，因为格式本身就是为此设计的。

`scan.rs` 的模块文档写得很清楚：识别一个 omy 文件**只需读开头 480 字节**，
载荷完全不碰，「一个 4 GiB 的加密视频与一个 1 KiB 的加密文本，扫描成本相同」。

放到云盘上，这个性质直接变成：

```
列目录（1 次 API 调用，拿到 N 个条目的 name/size/id）
    ↓
对每个候选文件发 1 次 Range 请求取前 480 B
    ↓
比对 magic "OMYFILE"+0x01 → 解析固定头 → 逐凭据试解 slot 区
    ↓
命中则补读 TLV 区（再几十到几百字节）→ 得到真实文件名、缩略图、媒体元信息
```

**扫 100 个文件只需下载约 48 KB**，而不是把 100 个文件下下来。

三个必须处理的现实问题：

**① 不能按扩展名过滤。** `ScanOptions` 默认 `extension_filter: None`，
注释说明了原因：伪装模式下文件可能叫 `.jpg`。云盘上同样成立。
但云盘上逐个探测有网络成本，所以给用户一个开关：默认只探 `.omy`
（快），可切「深度扫描」探全部（慢，要提示预计请求数）。

**② 必须并发，但要限流。** 480 B 的请求 RTT 远大于传输时间，串行扫 100 个
文件会等到天荒地老。用固定并发度（建议 8）+ 令牌桶，避免触发云盘风控。
这条要写进代码注释：**并发度不是性能调参，是风控边界**。

**③ 直链有有效期。** `get_res_download_url` 返回的是带签名和时效的 URL。
播放一个大视频时用户可能拖动几十分钟，直链早就过期了。所以
`CloudSource` 必须缓存直链并在 401/403 时**自动重取一次再重试**，
而不是把错误直接抛给播放器——那表现成「拖到后面就播不了」，
用户完全无从判断原因。

### 4.4 `CloudSource`：接上现有播放链路

```rust
/// 云盘上的一个 .omy 文件，实现 BlockSource 以复用全部现有解密/播放逻辑。
pub struct CloudSource {
    store: Arc<dyn RemoteStore>,
    file_id: String,
    header: FixedHeader,
    payload_start: u64,
    payload_len: u64,
    /// 直链缓存。过期要能自动续，否则长视频拖到后面就播不了。
    link: Mutex<Option<CachedLink>>,
}

impl BlockSource for CloudSource {
    fn header(&self) -> &FixedHeader { &self.header }

    fn read_ct(&self, offset: u64, len: u64) -> Result<Vec<u8>> {
        // HTTP Range: bytes=(payload_start+offset)-(…+len-1)
        // 401/403 时重取直链再试一次
    }

    fn ct_len(&self) -> u64 { self.payload_len }

    /// 必须为 true：UI 据此显示网络状态、调整预读策略（trait 文档原话）
    fn is_remote(&self) -> bool { true }

    fn describe(&self) -> String { format!("guangya:{}", self.file_id) }
}
```

一旦 `BlockSource` 实现好，**播放、缩略图、预览、部分解密全部零改动可用**——
这正是当初把它抽成 trait 的目的。

`source.rs` 里那条同步 trait 的决策（「远程实现在自己内部桥接异步」）在这里
兑现：`CloudSource` 内部用 `tokio` runtime handle 做 `block_on`，
不把异步污染到 `omy-core`。

## 5. 能力矩阵：只读位置该禁掉什么

### 5.1 唯一真相在后端

**前端不得自行推断能力。** 理由是 `RemoteScreen.vue` 顶部注释已经踩过的坑：

> 硬塞进 `EntryCard` 的话，每个分支都要写「如果是远端就……」，
> 而「远端不能加密」这类约束会散落在十几个地方——漏一处就是
> 用户点了加密然后收到一个没人看得懂的错误。

所以定义一个能力位图，由驱动声明，随位置一起下发给前端：

```rust
/// 一个远程位置支持哪些操作。
///
/// 这是**唯一真相**：前端的菜单禁用、后端的命令入口校验都读它。
/// 两处各自判断迟早漂移，症状是「菜单是亮的但点了报错」。
#[derive(Debug, Clone, Copy, serde::Serialize)]
pub struct Capabilities {
    pub read: bool,           // 列目录 + 下载（所有位置恒 true）
    pub write: bool,          // 上传新文件
    pub delete: bool,
    pub rename: bool,
    pub create_dir: bool,
    /// 能否原地改写已有文件的字节区间。
    ///
    /// 云盘**一律 false**：没有部分写 API，改密码槽这类操作要整文件重传。
    /// 与 write 分开是因为两者的失败后果完全不同。
    pub random_write: bool,
    /// 是否支持 HTTP Range。为 false 则无法流式播放，只能整取。
    pub range_read: bool,
}
```

### 5.2 各操作在只读云盘上的处理

| 操作 | 本地 | 云盘（读写） | 云盘（只读 OAuth） | 只读时怎么表现 |
|---|---|---|---|---|
| 浏览 / 识别 omy | ✅ | ✅ | ✅ | — |
| 预览 / 流式播放 | ✅ | ✅ | ✅ | — |
| 解密另存到本地 | ✅ | ✅ | ✅ | **保留**。这是只读位置最主要的用途 |
| 加密（就地） | ✅ | ✅ | ❌ | 菜单项**不出现** |
| 上传已加密文件 | — | ✅ | ❌ | 工具栏按钮不出现 |
| 删除 / 重命名 / 新建文件夹 | ✅ | ✅ | ❌ | 菜单项**不出现** |
| 改密码 / 加恢复码 | ✅ | ⚠️ 整文件重传 | ❌ | 只读时禁用并给 hint |
| 还原（覆盖原处） | ✅ | ⚠️ 需 delete+write | ❌ | 降级为「还原到本地」 |

**「不出现」还是「禁用置灰」怎么选？** 沿用 `RemoteScreen.vue` 已定的规矩：

> 共享是只读的，所以这里没有加密按钮。
> 不是「禁用」而是根本不出现——放个灰按钮反而让人反复去点

区分标准：
- **整个位置永远做不到**（只读云盘上的删除）→ **不出现**
- **当前状态做不到、换个状态就行**（文件没解锁所以不能改密码）→ **禁用 + hint**

前者放灰按钮是在骗人，后者的 hint 能告诉用户下一步该做什么。

### 5.3 落点：改一处，不是十处

`store.js` 的 `ctxItems` 已经是集中式能力门（每项都有 `disabled` + `hint`）。
只需在开头插入一段位置能力过滤：

```js
// store.js  ctxItems
const caps = currentPlaceCaps.value;   // 本地位置返回全能力

// 只读位置：写类菜单项整个不出现（而不是置灰）。
// 与容器内的处理保持一致——那里也是只留一条说明，不给会失败的操作。
const WRITE_KEYS = ['encrypt', 'delete', 'rename', 'new-folder',
                    'manage-key', 'recovery-generate'];
return items.filter((it) => caps.write || !WRITE_KEYS.includes(it.key));
```

**后端也要独立校验一遍。** 前端过滤只是体验，不是安全边界——
命令层必须在入口处拒绝，否则通过 devtools 直接 invoke 就绕过去了。
这两处的关系要在双方注释里互相标明（AGENTS.md 要求）。

## 6. UI / 交互设计

### 6.1 侧栏：云盘和本地位置并列

`SideBar.vue` 现在有「位置」和「设备」两组。新增第三组「云盘」：

```
位置
  🏠 主目录
  ⬇️ 下载
  💾 C:\
  ➕ 添加文件夹

云盘                        ← 新增
  🦆 光鸭云盘 · 我的账号      ← 已连接，可写
  🦆 光鸭云盘 · 只读          ← OAuth 授权，只读，带徽标
  ➕ 连接云盘

设备
  📡 管理设备
```

几个刻意的选择：

- **云盘单独分组，不混进「位置」。** 它们的响应延迟差一个数量级，
  混在一起用户会以为点进去卡住了。
- **只读位置在名字后面挂一个「只读」徽标**，而不是只在进去以后才知道。
  用户是在侧栏做决策的——「我要把这个文件加密到哪」这个念头发生在点击之前。
- **连接状态要在侧栏可见**（离线/令牌过期用灰色 + ⚠️）。令牌过期是
  云盘场景最高频的故障，藏在里面会让用户以为是网络问题。

### 6.2 主界面：复用 MainScreen，不新建 CloudScreen

这里与局域网远端的决策**相反**，需要说明理由。

`RemoteScreen.vue` 另起一套是对的，因为局域网共享「没有目录层级，是一份平铺
清单，用 handle 而非路径定位」——模型真的不同。

但**云盘有完整的目录层级**，能进能出，有面包屑，能新建文件夹（可写时）。
它和本地目录的模型是**同构的**，只是寻址用 ID 而非路径。这种情况下另起一套
会立刻踩中 AGENTS.md 里移动端那条教训的同款陷阱：

> 不要复制出一个 `MobileScreen`：列表、搜索、进度、统计的逻辑一样，
> 分成两份迟早出现「桌面修了的 bug 手机上还在」。

所以云盘复用 `MainScreen` + `EntryCard`，通过**位置能力**驱动差异，
而不是通过组件分叉。

### 6.3 必须补的视觉反馈

本地文件操作是毫秒级的，云盘不是。有三处现有 UI 不够用：

**① 面包屑要带位置标识。** 不然用户分不清现在在本地还是云上——
而这决定了「删除」意味着什么。

```
🦆 光鸭云盘 › 影视 › 2026        [只读]
```

**② 列表项要有「正在探测」的中间态。** 扫描 100 个文件要几秒，
现在的 UI 只有「加载中」和「加载完」两态。云盘上应当**边扫边出**：
条目先按云盘返回的名字列出来（灰色、无图标），探测到一个就原地变成
带锁图标或缩略图的形态。

不这样做的话，用户盯着一个空列表转圈几秒，而实际上第一个文件 200ms
就已经识别出来了。

**③ 网络错误要与「密码不对」严格区分。** `scan.rs` 已经立了规矩：

> 注意：这**不代表**文件损坏或密码错误——它可能属于另一个密码集。
> UI 应表述为「不属于当前密码」而非「密码错误」。

云盘上多出第三种：**没探测成功**（网络失败/限流/直链过期）。
这三者必须用三种不同的图标和文案：

| 状态 | 图标 | 文案 |
|---|---|---|
| 已解锁 | 缩略图 | 真实文件名 |
| 是 omy 但当前密码打不开 | 🔒 | 「不属于当前密码」 |
| **没能探测**（网络） | ⚠️ | 「未能读取，点击重试」 |

第三种混进第二种是最糟的结果——用户会以为自己密码记错了，
去反复试密码，而真正的问题是网络。

### 6.4 上传／加密到云盘的交互

可写位置上，「加密」有两种语义，必须让用户选：

```
加密 3 个文件
  ○ 加密后留在本地
  ● 加密后上传到 🦆 光鸭云盘 › 影视
     □ 上传成功后删除本地原文件      ← 默认不勾
```

「上传成功后删除本地原文件」默认不勾，且必须**先校验远端文件完整**
（比对大小 + 头部 magic 复读）再删。这是数据丢失的高危路径，
对应 AGENTS.md 里「平台不支持某能力时明确报不支持，不要静默降级」的同款
谨慎——只不过这里是「没确认成功就不要删」。

### 6.5 移动端

按 AGENTS.md 的响应式规则，有两条必须一并处理：

- 云盘列表项的打开同样要读 `isMobile` 走单击分支，不能只绑 `dblclick`。
- 云盘操作耗时长，移动端切后台会被系统挂起。传输中要给出明确提示，
  并在恢复时如实报告「已中断」而不是假装还在传。

## 7. 原子性与一致性：诚实地降级

### 7.1 云盘上做不到真正的原子写

本地的五步流程在云盘上只能退化成：

```
1. 上传到临时名 <target>.omy.uploading
2. 校验：比对返回的 size + 重新 Range 读前 480 B 验 magic 与头部 MAC
3. 改名为 <target>.omy
4. 失败时清理临时文件（尽力而为）
```

第 3 步不是原子的。极端情况下会留下 `.uploading` 残留文件。

**处理方式是如实声明，不是假装解决：**
- 扫描时识别 `.uploading` 后缀并在 UI 标为「未完成的上传」，提供清理入口。
- 文档里明确写出这条限制，不要让用户以为云盘上的写入和本地一样安全。

理由同 AGENTS.md：「平台不支持某能力时，明确报不支持，不要静默降级」。

### 7.2 改密码这类原地改写

`reencrypt.rs` 在本地是改头部若干字节。云盘上没有部分写 API，
必须整文件下载→改→重传。一个 4 GiB 的视频改个密码要传 8 GiB。

首期的处理：**`random_write: false`，改密码在云盘位置上禁用**，
hint 写明「请先还原到本地再操作」。等确认有人真的需要再做整文件重传方案——
过早实现一个要传 8 GiB 的功能，比没有这个功能更糟。

## 8. 密文缓存

远程位置不缓存是不可用的：`read_range` 解一个块要先取整块密文，
播放器每秒发若干次读请求，没有缓存就是每次都走网络。

### 8.1 只缓存密文，这条是硬约束

**缓存里存的必须是从远端原样取回的密文字节，解密后的明文一律不落盘。**

这不是性能取舍，是威胁模型的边界。项目的核心安全目标就是「明文不落盘」
（`remote.rs` 顶部把它列为照搬 CLI 做法会踩的两条红线之一）。
缓存目录如果混进明文，等于在用户毫不知情的情况下，把他特意加密的内容
以明文形式写回磁盘——而且是长期留存、不随进程退出消失的那种。

缓存密文则完全没有这个问题：**那些字节在云盘上本来就是公开存放的**，
缓存到本地不增加任何泄露面。攻击者拿到缓存目录，得到的和他去扒云盘
是一样的东西。

由此推出两条实现约束：

- 缓存的写入点必须在 `CloudSource::read_ct` 里（拿到密文、还没解密时），
  **不能**放在 `read_source_range` 之后。
- 缓存键不能用文件名（那是解密出来的信息）。用
  `blake2(vault_salt ‖ file_uuid ‖ block_index)` ——`file_uuid` 在固定头里，
  本来就是明文可见的。

### 8.2 缓存什么，分两层

| 层 | 内容 | 大小 | 策略 |
|---|---|---|---|
| **头部缓存** | 每个文件前 480 B~几 KB | 极小 | **常驻**，不计入用户设的上限 |
| **载荷块缓存** | 按 `chunk_size` 对齐的密文块 | 大 | LRU，受上限约束 |

头部单独一层且不淘汰，是因为它的收益/成本比高到没有取舍余地：
一个文件几 KB，却决定了「列表能不能显示真实文件名和缩略图」。
淘汰掉它会让用户每次回到目录都要重新扫一遍——扫 100 个文件就是 100 次
网络往返，而它们加起来还不到 1 MB。

**头部缓存要能失效。** 文件在云端被改过（改密码、重传），头部就变了。
用 WebDAV 的 `ETag` / `Last-Modified` 或云盘返回的修改时间做校验；
拿不到这些信息时（部分 WebDAV 服务端确实不给），退化为按 size 比对
并设较短的 TTL。**不要假装能检测到**——检测不到就诚实地设短 TTL。

### 8.3 块对齐：不缓存任意区间

播放器请求的区间是任意的，但缓存必须**按加密块边界对齐**存。
理由是格式本身决定的：AEAD 分块加密，解密的最小单位就是一个块。
按任意区间缓存会出现大量互相重叠的碎片，既浪费空间又无法命中。

所以 `read_ct(offset, len)` 进来后先扩展到块边界，
按块查缓存 → 缺哪块取哪块 → 取回的块整块入缓存。

### 8.4 用户可设的上限

```
设置 › 远程位置 › 缓存

  缓存位置    C:\Users\...\AppData\Local\omy\cache      [更改] [打开]
  已用空间    1.2 GB / 2.0 GB   ▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░

  最大缓存    [  2 GB  ▾]     512 MB / 1 GB / 2 GB / 5 GB / 10 GB / 自定义 / 不限制

  □ 退出应用时清空缓存
  
  [清空缓存]   ← 显示将释放多少

  ⓘ 缓存中只存放加密后的密文，与云端文件内容相同；解密后的内容不会写入磁盘。
```

几个刻意的设计：

- **默认 2 GiB。** 够放下一部 4K 电影的可观片段，又不会让用户在某天
  发现 C 盘被吃掉几十 GB。
- **「不限制」要给，但不做默认。** NAS 用户和大容量磁盘用户确实需要它。
- **必须显示缓存位置并能更改。** 移动端和小 SSD 的机器上，用户需要
  把它挪到别的盘。更改后要迁移已有缓存或提示将被清空，不能静默丢弃。
- **那行说明文字不能省。** 用户看到「缓存」两个字的第一反应是
  「我的文件被明文存下来了？」——这恰恰是本项目最需要澄清的疑虑。
- **超限淘汰按 LRU，但正在播放的文件豁免。** 否则播放一个比缓存上限
  还大的视频时，会一边下一边把自己刚下的块淘汰掉，表现为无限循环下载。
  这条要写进注释，它是很容易在实现时漏掉的自噬行为。

### 8.5 加密缓存要不要做

**首期不做，但要留口子。**

缓存的是密文，不加密也不泄露内容（§8.1）。但有一个次级信息会泄露：
**哪些文件被访问过、访问了哪些片段**。对「防止文件被直接访问和识别内容」
这个威胁模型来说，这是可接受的——`01-requirements-and-threat-model.md`
已经接受了「文件可被识别为加密文件」这一前提。

留的口子是：缓存索引与数据分离，将来要加密时只需替换存储层。

### 8.6 与现有 `TempPlaintext` 的关系

`fsatomic.rs` 里的 `TempPlaintext` 处理的是「用外部应用打开」时的明文临时
文件，它有完整的旁路防护（缩略图缓存、搜索索引、残留）。

**两者不要混用，也不要共用目录。** 一个是密文长期缓存，一个是明文短期
临时文件，生命周期和清理策略完全相反。放一起迟早出现「清缓存时漏清了
明文文件」或者反过来「把正在用的明文文件当缓存淘汰了」。

## 9. 测试策略

按 AGENTS.md 的要求，每条断言都要能抓到真实缺陷。

| 层 | 测什么 | 关键断言（附「不这样会怎样」） |
|---|---|---|
| `omy-core` 单测 | `probe_bytes` | 给 479 B 必须报 `Truncated` 而非「不是 omy 文件」——否则网络截断会被误报成文件类型错误 |
| `omy-cloud` 单测 | `Capabilities` 序列化 | 字段名不能变。变了前端读到 `undefined`，`!caps.write` 为真 → 只读位置反而全部可写 |
| **`omy-cloud` 单测** | **缓存里没有明文** | 造一个已知明文串的文件，走完整读取链路，然后**扫描整个缓存目录确认该串不出现**。这是 §8.1 那条硬约束唯一靠得住的验证方式 |
| **`omy-cloud` 单测** | **LRU 不自噬** | 缓存上限设 10 MB，读一个 50 MB 文件，断言正在读的块不被淘汰、总请求数不超过块数 × 1.5。不这样会无限循环下载 |
| **`omy-cloud` 单测** | **超限淘汰** | 写到上限 + 1 后，总占用必须回落到上限内，且淘汰的是最久未用的 |
| mock HTTP | WebDAV Range | 服务端返回 206 + `Content-Range` 要正确拼接；返回 200（忽略 Range）时要能识别并回退，而不是把整文件当成一个区间 |
| mock HTTP | 直链过期重取 | 首次 403、重取后 200，必须最终成功。不这样则长视频拖到后面就播不了 |
| mock HTTP | 限流退避 | 429 要退避重试而非直接失败 |
| GUI 端到端 | 只读位置菜单 | 按**结构（`data-mi`）**定位，不按文字——AGENTS.md 明确要求 |
| 变异测试 | 去掉 `caps.write` 过滤 | 必须被抓到。存活说明能力门形同虚设 |
| 变异测试 | 把缓存写入点移到解密之后 | 必须被「缓存里没有明文」那条抓到 |

**需要真实服务端的手工验证清单**（自动化测不了的部分）：
对 Nextcloud 与至少一个 AList 中转实例各跑一遍——上传 1 GiB 文件、
拖动播放 4K 视频、断网恢复、缓存写满后继续播放。

## 10. 分期

| 期 | 范围 | 交付判据 |
|---|---|---|
| **P0** | `RemoteStore` trait + `Capabilities` + `probe_bytes` + 前端能力门 | 现有局域网远端改为走同一套能力位图，行为不变（回归绿） |
| **P1** | **WebDAV 只读**：PROPFIND 列目录 + 探测 + `CloudSource` 流式播放 + 密文缓存 | 能在 Nextcloud / AList 上认出 omy 文件并拖动播放 4K 视频 |
| **P2** | **WebDAV 可写**：上传 + 删除 / 改名 / 新建目录 + 缓存设置界面 | 加密后直传，校验通过后可选删本地；缓存上限生效 |
| **P3** | 私有云盘驱动（光鸭优先）+ 令牌加密持久化 | **仅在确有需求时启动**，见 §3.3 |

P0 单独成期是有意的：**先让现有的局域网远端也走这套能力位图**，
用一个已知正确的场景验证抽象本身，再接第一个远程存储。
直接上 WebDAV 会同时引入「抽象对不对」和「驱动对不对」两个变量，
出问题时无法二分。

## 11. 待定问题

1. **私有云盘驱动接哪家、什么时候接。** 按 §3.3，WebDAV 落地后按真实需求
   决定。真要接时最合理的顺序是 115 / 123（有正式开放平台和自助开发者门户，
   不必走网页版接口）优先于光鸭（目前只能走网页版 client_id）。
2. **缓存要不要跨会话共享给局域网远端。** 局域网远端同样在反复拉密文，
   理论上能复用同一套块缓存。但两者的失效条件不同（对端可能随时下线），
   合并前要想清楚，否则会出现「对端已经换了文件，本地还在用旧块」。
3. **WebDAV 的 `vendor` 差异要覆盖到什么程度。** rclone 维护了 8 个 vendor
   分支，我们用到的子集小得多。先按 `generic` 实现，等真实服务端暴露问题
   再加分支——**不要照着 rclone 的列表预先写八套代码**，那些分支有一半
   是为我们用不到的功能（修改时间、哈希、分块上传）准备的。
