# 12 · 决策记录

> 记录关键设计决策的**理由**，特别是**被否决的方案**和**推翻过的判断**。
> 目的：后来者（包括未来的自己）能看懂"为什么是这样"，避免重新踩坑或误以为某个方案没被考虑过。

---

## DEC-01 · 分块 AEAD，而非帧级加密

**背景**：用户问「视频可以直接播放、拖动随意观看任意位置，这可能需要帧加密？（我不清楚，你自行调研）」

**结论**：不用帧加密，用**固定大小分块 AEAD + HTTP Range**。

**理由**：

| 方案 | 问题 |
|---|---|
| DRM 式帧加密（ISO CENC） | 容器元数据保持明文才能被播放器解析 → **泄露时长、分辨率、编码、章节、字幕轨信息**；实现复杂度翻倍；只覆盖特定容器 |
| **分块 AEAD**（采用） | 整个文件（含容器结构）全部密文；块索引 O(1) 定位；格式无关 |

分块 AEAD 是 age、Google Tink、RFC 8188 的通行做法，IETF 也在标准化 raAE（random-access AEAD）。

**代价**：seek 时需解密 1–2 个完整块（256 KiB 默认），而非精确到帧。实测本地场景 <100 ms，可接受。

## DEC-02 · 两级 KDF（Argon2id → HKDF）

**背景**：多密码扫描要求"给定 N 个密码，快速判断某文件是否匹配"。

**结论**：每密码每会话跑一次 Argon2id 得到 KEK，再用 HKDF 为每个文件微秒级派生子密钥。

**实测依据**：

| 操作 | 耗时 |
|---|---|
| Argon2id (m=64MiB, t=3, p=1) | 180 ms |
| HKDF 单次 | 13.2 µs |
| **比值** | **~13,700×** |
| 扫描 500 文件 × 5 密码 | 170 ms |
| 对照：每文件独立 Argon2 | 394 s（慢 2,324×） |

10,000 文件推算 ~3.4 s；若每文件独立 Argon2 需约 2.5 小时——**功能根本不可用**。

**所以两级 KDF 不是性能优化，是可行性前提。**

## DEC-03 · ❌ 已否决：`kek_id` 前缀比对加速扫描

**这是我在澄清过程中提出后又主动推翻的方案，记录在此避免重蹈。**

**最初提议**：在文件头存一个 `kek_id`（KEK 的哈希前缀），扫描时先比对 `kek_id` 再尝试解密，跳过不匹配的文件。

**为什么否决**：

1. **泄露密码关联性** —— 攻击者能看出"这 300 个文件属于同一个密码"，直接破坏 D-02 可否认性。
2. **根本没有必要** —— 有了 DEC-02 的两级 KDF，每文件试解密只需 13.2 µs。500 文件 × 5 密码 = 170 ms 已经足够快，`kek_id` 带来的加速微不足道。

**教训**：在引入会泄露信息的优化前，先确认基线方案真的不够快。这里是我先入为主假设"逐个试解密会很慢"，实测后发现假设错了。

## DEC-04 · ❌ 已否决：MP4 faststart 重整

**这是用户直接质疑并纠正了我的判断的一处，且结论比我最初和用户设想的都更好。**

**我最初的说法**：MP4 的 `moov` box 若在文件尾部，播放器需要先 seek 到尾部才能开始播放；建议做 faststart 重整（把 moov 移到头部）。但这会改变文件字节，与 D-07（bit-for-bit 还原）冲突，需二选一。

**用户的质疑**：

> 「加密文件必须能完整还原，你说的 faststart 我看上去好像也能还原成原文件呀，不支持吗？」

**核实结果：用户是对的，而且比他想的更好。**

1. faststart 本身**是可逆的** —— 只是 box 顺序调整，记录足够信息即可还原。用户的判断成立。
2. **但更关键的是：本地 Range 场景根本不需要 faststart。**
   - faststart 在 Web 上是刚需，是因为跨公网每次 seek 都要付一个 RTT（几十到几百毫秒）
   - 本地读取 moov 在尾部只是多 2 次 seek，微秒级
   - 所以问题从一开始就不存在

**最终方案**：把 `moov` 位置与内容**缓存进 header TLV**。首次打开时解析记录，之后直接命中——**比 faststart 还快，且原文件零改动**。

faststart 已从设计中完全删除。

**教训**：遇到"经典优化手段"时，先确认它要解决的瓶颈在当前场景下是否真的存在。Web 场景的经验不能直接搬到本地场景。

## DEC-05 · ❌ 已否决：预先 remux 存进去

**考虑过**：加密时就把 MKV remux 成 MP4 存进去，播放时直接 P1 直通。

**否决理由**：MKV 的 EBML 结构（CueTime 精度、SimpleBlock 与 BlockGroup 的选择、Void 填充、轨道顺序）难以字节级还原，与 D-07 冲突。

**替代**：播放时实时 remux（P2 路径），原文件保持不动。

> 用户后来主动提出的 D-26「转码选项」在功能上覆盖了这个需求，但**明确标注为不可还原**并需二次确认——把选择权交给用户，而不是替用户做不可逆的决定。

## DEC-06 · MKV remux 命中率被高估

**调研中的一个反直觉发现，影响了播放路径的预期设定。**

直觉上"大部分 MKV 是 H.264+AAC，remux 到 MP4 就能直通"。**实际不成立**：

- 若片源是 H.264+AAC，当初大概率就直接封成 MP4 了
- 用户手上是 MKV，**恰恰因为装了 MP4 装不下的东西**：DTS-HD / TrueHD / FLAC / Vorbis 音轨，PGS / VobSub / ASS 字幕

而这些**无法封入 MP4**：DTS/TrueHD/Vorbis 不在 MP4 标准编码之列；PGS/VobSub 无法转 `mov_text`。

**结论**：P2（remux）的实际命中率远低于直觉，P3（全解码）是必需的兜底，不能省。这也是 D-11（采用 FFmpeg）成立的重要依据。

## DEC-07 · 采用 FFmpeg，GUI 接受 GPL-3.0

**背景**：我给出三个方案并推荐 (a+)：

| 方案 | 兼容性 | 许可证影响 |
|---|---|---|
| (a) 只支持 WebView 原生格式 | 低 | 无 |
| (b) remux | 中 | LGPL |
| (c) 完整 FFmpeg | 高 | LGPL（仅解码）/ GPL（含编码器） |

**用户选择 (c)**，追求最大兼容性。

**连锁后果**：
- GUI 与 CLI 变为 GPL-3.0
- 但 `cvault-core` 保持 MIT/Apache-2.0（零 FFmpeg 依赖）—— 这是刻意的架构约束，保证格式能被任何人集成
- 移动端 FFmpeg 成为持续维护负担（FFmpegKit 2025-04 退役、Play 16 KB 页对齐）→ 促成 D-24

详见 [10 号文档](10-licensing-and-patents.md)。

## DEC-08 · HEIC 分层策略

**用户问**：「专利风险是啥？开源软件不能用吗」

**澄清的误解**：版权许可 ≠ 专利许可。代码可自由分发，不等于拿到了专利实施许可。

**方案**：系统解码器优先 → libheif 可选 feature（默认关闭）→ 官方包不含软解。与 Firefox/Chromium 的做法一致，把专利责任转移给已获授权的 OS 厂商。

**关键边界**：**加密功能永不受影响**。任何格式都能加密和 bit-for-bit 还原，只是能否**预览**取决于解码器。这一点必须在 UI 上说清。

---

## DEC-09 · 转码选项与"必须完整还原"的冲突

**用户新增需求**：

> 「既然加了 FFmpeg，那加密时也添加一个视频转码选项，用户可选择转为 web 原生支持的格式再加密，避免后续性能问题」

**识别出的冲突**：这与 D-07（bit-for-bit 还原）**直接矛盾**。转码是有损且不可逆的。

**处理方式**：不替用户做决定，而是给出三种模式 + 强制警告：

| 模式 | 行为 | 可还原 |
|---|---|---|
| `none`（默认） | 原样加密 | ✅ |
| `web` | 转码后加密 | ❌ 需二次确认 |
| `dual` | 原文件 + 播放副本都存 | ✅（体积翻倍） |

选择 `web` 时 UI 与 CLI 都必须显示不可逆警告（见 08 §3.3、09 §5.1）。原文件 SHA-256 会记录在 header 中供核对，但无法据此还原。

## DEC-10 · 🐛 参考实现真 bug：批量加密每文件重跑 Argon2

**这是写参考实现时发现的真实缺陷，同时暴露了生产实现必须遵循的正确姿势。**

初版 `EncryptParams` 只接受 `passwords`，导致批量加密时**每个文件都重新跑一次 Argon2**（180 ms × N）。

**修复**：增加 `keks` 字段，允许传入预派生的 KEK。

**对生产实现的要求**：CLI 与 GUI 的批量操作必须复用同一次 KDF 结果。这条已写入 [09 号文档 §5.1](09-cli-design.md)。

## DEC-11 · 🐛 文件名 padding 的长度泄露 bug

**由交叉验证脚本抓出的真实缺陷。**

**原公式**：

```python
bucket = (len // 64 + 1) * 64
```

**问题**：当 `len = 63` 时，`bucket = 64`，但实际需要 `2 + 63 = 65` 字节（2 字节长度前缀）→ **负填充**，padded 长度变成 65，越出桶边界。

**后果**：该长度的文件名反而**暴露自己的长度特征**——本来 padding 就是为了隐藏长度，结果特定长度被单独标记出来。这是安全性缺陷，不只是逻辑错误。

**修复**：基于实际需要的字节数计算：

```python
need = 2 + len(name_utf8)
bucket = ceil(need / 64) * 64
```

**修复后验证**：长度 0–199 及 250 / 300 的文件名落入 5 个桶，同桶内 `header_len` 完全唯一（无法从 header 长度反推文件名长度）。

**教训**：padding 类逻辑必须基于"最终写入的总字节数"计算，而不是"原始数据长度"。已列为 Rust 实现的必测边界（见 11 号文档 §4.3）。

## DEC-12 · 🐛 测试断言本身的方法学错误

**这是我自己设错了阈值，值得记录，因为它是一类容易自欺的错误——测试通过了不代表测试是对的。**

### 错误一：用"字节覆盖率"检测随机性

原断言：slot 区的字节覆盖率应 > 85%。

**错在哪**：384 字节样本对 256 种可能取值是**严重欠采样**。理论期望覆盖率仅约 77.7%（生日问题），所以 85% 的阈值本身就不可能达到——即使数据是完美随机的。

**修正**：改为与**同长度纯随机对照组**做统计检验。

### 错误二：用固定阈值比较熵差

原断言：真实 slot 段与填充段的熵差应 < 0.35。

**错在哪**：实测两段**纯随机**数据（144 B vs 240 B）的熵差中位数就有 **0.456**——短样本的熵估计对长度极度敏感。用固定阈值必然误判。

**修正**：改为与随机基线的 p95 比较。

**最终验证结果**：slot 区熵 7.491 bits/byte，落在纯随机基线区间 [7.332, 7.508] 内 ✅

**教训**：对随机性/熵的断言，必须用同分布对照组，不能拍脑袋定阈值。否则要么永远失败，要么永远通过——两种情况下测试都没有价值。

## DEC-13 · 可否认性的真实边界

**实测**：1 密码文件与 3 密码文件均为 **772 B，字节结构完全相同**。slot 区始终填满 8 个（真实 slot + 随机填充），无法从文件本身判断实际有几个密码。

**但必须诚实说明其局限**：

- ✅ 能抵抗：静态文件分析
- ❌ **不能**抵抗：文件系统时间戳关联、备份历史对比、内存取证、用户自己的操作痕迹

这符合 D-01 的威胁模型（"避免直接访问和识别"），但**不是隐藏卷级别的可否认性**。UI 中不得暗示后者（见 08 §6.2 的伪装模式说明文案）。

## DEC-14 · 扫描缓存只放内存

**用户决策 D-19**。

**理由**：落盘索引会产生新的泄露面——"文件加密了，但索引里有明文文件名"是典型的自相矛盾。

**代价**：每次启动需重新扫描。实测 10,000 文件约 3.4 s，可接受。

---

## DEC-15 · 局域网只传密文、只读

**用户决策 D-04 + D-21**。

**架构影响**：`BlockSource` trait 让远程与本地走同一套上层逻辑（见 11 号文档 §1.2）。远程实现返回密文块，解密统一在客户端完成——服务端**从不持有明文**。

**只读**的额外好处：不需要处理并发写冲突、权限提升、远程删除等一大类问题。
