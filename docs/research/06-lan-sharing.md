# 06 · 局域网共享

> 用户决策：**只传密文**（D-04）、**只读不可写**（D-21）、有效期与吊销机制由设计方拟定。

## 1. 核心原则

```
┌─────────────── 设备 A（共享方）────────────────┐
│  持有：密文文件                                │
│  不知道：对方的密码                            │
│  提供：密文字节区间（Range 服务）               │
└────────────────────┬───────────────────────────┘
                     │  加密信道（只传密文）
┌────────────────────▼───────────────────────────┐
│  设备 B（浏览方）                              │
│  持有：自己的密码 → 自己派生 KEK               │
│  执行：本地解密                                │
└────────────────────────────────────────────────┘
```

**服务端退化成纯密文块服务器**，永远不接触密码、KEK、FEK 或明文。

这带来一个重要性质：**即使设备 A 被完全攻陷，攻击者也只能拿到密文**——与文件放在不可信云盘上是同等风险级别。

---

## 2. 架构：复用同一套块寻址

远程播放与本地播放的唯一区别是"密文块从哪来"：

```rust
/// 块来源抽象 —— 本地与远程复用同一套 Range 逻辑
trait BlockSource: Send + Sync {
    /// 读取密文的任意字节区间
    async fn read_ct_range(&self, offset: u64, len: u64) -> Result<Bytes>;
    /// 密文总长度
    fn ct_size(&self) -> u64;
}

struct LocalFileSource { path: PathBuf }
struct RemoteHttpSource { peer: PeerId, file_handle: FileHandle }
struct ShardedSource { shards: Vec<ShardRef>, holes: Vec<Range<u64>> }
```

**远程 seek 的完整链路**：

```
设备 B 的播放器 seek 到 t 秒
  → 本地自定义协议收到 Range 请求
  → 明文偏移 → 块号 → 密文偏移（O(1) 公式，与本地完全相同）
  → RemoteHttpSource 向设备 A 请求该密文区间
  → 设备 A 返回密文（它不知道这是什么内容）
  → 设备 B 用自己的 FEK 解密
  → 返回明文切片给播放器
```

⚠️ **绝不能写两遍寻址逻辑**——这是设计上的硬性要求，否则本地和远程行为会逐渐分叉。

## 3. 设备发现

### 3.1 mDNS / DNS-SD

```
服务类型：_omy._tcp.local
TXT 记录：
  v=1                          协议版本
  id=<设备公钥指纹前8字节>       用于识别，非敏感
  name=<用户设定的设备名>        如 "书房台式机"
```

⚠️ **TXT 记录中不放任何敏感信息**——mDNS 广播在整个局域网可见。

### 3.2 平台注意事项

| 平台 | 要点 |
|---|---|
| **iOS 14+** | **必须**声明 `NSLocalNetworkUsageDescription` + `NSBonjourServices`，首次使用会弹系统授权框。用户拒绝后**无法再次弹出**，只能引导去设置里开启 |
| **Android** | NSD API（`NsdManager`）。部分厂商 ROM 的省电策略会杀掉 mDNS 监听 |
| **Windows** | 防火墙首次会弹出询问；需在安装时或首次使用时申请规则 |
| **macOS** | Bonjour 原生支持，但沙箱应用需 `com.apple.security.network.server` 权限 |
| **Linux** | 依赖 Avahi，部分精简发行版未预装 |

### 3.3 手动连接兜底

mDNS 在很多网络环境下不可靠（企业网络禁用组播、跨网段、AP 隔离）。**必须提供手动输入 IP + 端口**的方式。

## 4. 配对与信道安全

### 4.1 首次配对：PAKE

使用 **SPAKE2** 或 **CPace**（平衡型 PAKE）：

```
设备 A 显示：
  ┌──────────────────┐
  │   配对码：4B7F   │      或   [二维码]
  │   有效期 60 秒   │
  └──────────────────┘

设备 B 输入 4B7F
  → 双方用短 PIN 执行 SPAKE2
  → 派生共享密钥
  → 交换并确认长期设备公钥（X25519）
  → 配对完成，PIN 作废
```

**为什么用 PAKE 而不是直接传密码**：PAKE 能用**低熵的短 PIN** 建立**高熵的安全信道**，且抵抗离线字典攻击——攻击者每次猜测都必须与真实设备交互一次。

**必须的防护**：
- PIN 随机生成（不允许用户自定义弱 PIN）
- 有效期 60 秒
- 失败 3 次后作废并重新生成
- 显示 SAS（Short Authentication String）供双方目视比对，防中间人

### 4.2 长期信道

配对完成后使用长期设备密钥：

| 方案 | 说明 | 推荐 |
|---|---|---|
| **Noise Protocol (IK 模式)** | 轻量、无证书、专为 P2P 设计 | ⭐ 推荐 |
| TLS 1.3 + 自签名证书固定 | 生态成熟，但证书管理繁琐 | 备选 |

Noise IK 模式：发起方已知响应方静态公钥，1-RTT 建立，提供前向保密。

### 4.3 为什么不能裸 HTTP

即使只传密文，裸 HTTP 也不可接受：
- 攻击者可篡改密文（虽然 AEAD 会检测，但会造成拒绝服务）
- 泄露访问模式（哪个文件、哪个区间、什么时候）
- 泄露文件大小和数量
- 无法验证对端身份

## 5. 共享粒度与权限（决策 D-21）

### 5.1 开启共享时选择范围

```
📡 开启局域网共享

  共享内容：
    ☑ 工作资料/          (1,247 文件, 3.2 GB)
    ☐ 私人照片/          (8,432 文件, 45 GB)
    ☑ 影视/纪录片/       (23 文件, 89 GB)

  权限：只读（不可修改、不可删除、不可上传）

  有效期：
    ○ 仅本次会话（关闭应用即失效）
    ◉ 24 小时
    ○ 7 天
    ○ 永久（不推荐）

  允许的设备：
    ◉ 仅已配对设备
    ○ 任何设备（需输入配对码）
```

### 5.2 权限模型

**只读，硬性约束**（决策 D-21）：

| 操作 | 允许 |
|---|:---:|
| 列出共享目录内的文件 | ✅ |
| 读取密文的任意区间 | ✅ |
| 读取 header | ✅ |
| 写入 / 修改 | ❌ |
| 删除 | ❌ |
| 上传新文件 | ❌ |
| 访问共享范围外的路径 | ❌ |

**服务端实现要点**：
- 路径必须经过规范化 + 前缀校验，**防目录穿越**（`../`、符号链接逃逸、Windows 8.3 短名、UNC 路径）
- 只暴露不透明的 `file_handle`，**不暴露真实路径**
- 请求的字节区间必须在文件范围内，超出返回 416

### 5.3 有效期与吊销（本设计拟定）

| 机制 | 设计 |
|---|---|
| **会话有效期** | 用户选择，默认 24 小时。到期后需重新授权 |
| **心跳与自动断开** | 60 秒无活动的连接自动关闭；重连需重新握手 |
| **单方面吊销** | 任一端可随时吊销配对，立即断开且需重新配对 |
| **设备列表管理** | 显示所有已配对设备、最后连接时间、当前状态；可逐个吊销 |
| **共享方锁定时** | **继续服务**（决策 D-30，见 §5.5） |
| **访问日志** | 本地留痕：哪台设备、什么时间、访问了哪些文件。**仅本地保存，不上报** |

### 5.5 共享方锁屏后继续服务（决策 D-30）

> ⚠️ **本节推翻了本文档早期版本的描述**。原文写「共享方 vault 锁定 →
> 立即停止服务（因为连列出文件都需要解密 header）」，括号里的理由是错的，
> 结论也因此是错的。

**服务端根本不需要任何密钥**。这与 §1 的核心原则一致——服务端是纯密文
块服务器。三种服务端操作所需的信息全部位于**未加密的固定头**中：

| 操作 | 需要什么 | 是否需要密钥 |
|---|---|---|
| `LIST` | magic 识别 + 文件大小 | ❌ |
| `STAT` | `header_len`、`file_uuid`、密文总长 | ❌ |
| `READ` | 按偏移读字节 | ❌ |

`LIST` 返回的文件名**本来就是密文**（§6.1 已写明「服务端不解密，
由客户端用自己的 KEK 解」）。既然不解密，自然不需要 KEK。

已用真实加密文件验证（`omy-core/examples/verify_keyless_serve.rs`，5 项断言）：
全程不构造任何 `Kek`，`is_omy_file`、`peek_header`、任意区间读取
全部正常；同时反证 `open(&[])` 必定失败——**零密钥是真的零**，
服务端读不到文件名与内容。

**因此锁屏后继续服务不但可行，而且更符合安全模型**：

- 服务进程持有的东西不因锁屏而改变（本来就只有密文）
- 锁屏停服反而制造了一种错觉，好像服务端平时握有某种敏感状态
- 用户体验上，"A 设备锁屏导致 B 正在看的视频中断"没有安全收益

**实现约束**（这些才是真正需要守住的）：

1. 服务端进程**绝不允许**持有 `Kek` / `Fek` / 明文——用类型系统保证，
   而不是靠约定：服务层的数据源只接受"读密文字节"这一种能力。
2. 共享范围在**开启共享时**固化为具体路径集合，不依赖 vault 解锁状态。
3. 锁屏时 GUI 侧必须清空自己的密钥（这条不变），但**共享服务不受影响**。
4. 用户可在设置里选择"锁屏时暂停共享"，默认关闭——有人会希望离开电脑
   时彻底静默，这是偏好而非安全需求。


### 5.4 访问日志格式

```
2026-08-29 14:23:11  书房台式机  连接
2026-08-29 14:23:15  书房台式机  列出 <共享点 #1>
2026-08-29 14:25:03  书房台式机  读取 handle=a3f9… (完整, 2.3 MB)
2026-08-29 14:31:47  书房台式机  读取 handle=7c21… (0-15%, 127 MB)
2026-08-29 15:02:19  书房台式机  断开
```

⚠️ **日志里不可能有明文文件名**——服务端零密钥（§5.5），它自己就
不知道那个 handle 对应什么文件。这不是遗漏，是必然结果。

早期版本的示例写成「读取 季度报告.docx」，那要求服务端能解密文件名，
与零密钥模型直接冲突。现在记不透明 handle + 磁盘路径的哈希前缀。

对用户而言可读性确实变差了。补偿办法：**解锁状态下查看日志时，
由 GUI 层用当前 KEK 把 handle 还原成文件名再显示**——解密发生在
查看端而非记录端，日志文件本身仍不含明文。

日志只在内存中保留当前会话，进程退出即清空；用户显式导出时才落盘，
且落盘时按普通 omy 文件加密。

## 6. 传输协议

### 6.1 接口设计

在 Noise 加密信道之上，使用简单的请求-响应协议：

| 请求 | 参数 | 响应 |
|---|---|---|
| `LIST` | 共享点 ID, 路径 | 条目列表（名称密文、大小、类型、file_handle） |
| `STAT` | file_handle | 文件大小、header_len |
| `READ` | file_handle, offset, len | 密文字节 |
| `PING` | — | pong（心跳） |

**注意 `LIST` 返回的是密文文件名**——服务端不解密，由客户端用自己的 KEK 解。

### 6.2 分块传输与流控

- 单次 `READ` 上限：4 MiB（防止一次请求耗尽内存）
- 大范围读取由客户端拆分为多次请求
- 支持并发请求（提高吞吐），但限制单连接并发数（默认 4）

### 6.3 网络优化

| 优化 | 说明 |
|---|---|
| **预读** | 顺序播放时预取后续块，隐藏网络延迟 |
| **自适应块大小** | 网络质量好时批量请求更大区间，减少往返 |
| **moov 缓存的价值** | 远程播放时，从 header TLV 直接拿 moov 可省掉 2 次网络往返——**这是远程场景收益最大的优化** |
| **连接复用** | 单个 Noise 会话上多路复用，避免反复握手 |

## 7. 安全考量

### 7.1 服务端的攻击面

即使只传密文，服务端仍有风险：

| 风险 | 缓解 |
|---|---|
| **目录穿越** | 路径规范化 + 前缀校验 + 不暴露真实路径 |
| **DoS（大量连接/大请求）** | 连接数上限、请求速率限制、单请求大小上限 |
| **资源耗尽** | 限制并发读取、限制内存缓冲 |
| **信息泄露（错误消息）** | 统一错误响应，不暴露路径或内部状态 |
| **未授权访问** | 只接受已配对设备；每个请求校验会话有效性 |

### 7.2 客户端的信任假设

设备 B 从设备 A 拿到的密文**可能是恶意构造的**（如果 A 被攻陷）。但：

- ✅ AEAD 会检测任何篡改
- ✅ header MAC 会检测参数篡改
- ⚠️ **但解析 header 本身的代码必须是健壮的**——恶意 `header_len`、`tlv_len`、`entry_count` 可能导致内存耗尽或整数溢出

**强制要求**：
```rust
// 所有从不可信输入读取的长度字段都必须校验上界
const MAX_HEADER_LEN: u32 = 64 * 1024 * 1024;   // 64 MB
const MAX_TLV_LEN: u32 = 32 * 1024 * 1024;
const MAX_INDEX_ENTRIES: u32 = 16 * 1024 * 1024;

if header_len > MAX_HEADER_LEN { return Err(Malformed); }
// 且所有偏移计算使用 checked_add / checked_mul
```

### 7.3 不做的事

| 不做 | 原因 |
|---|---|
| 跨互联网访问 / 内网穿透 | 显著扩大攻击面；用户可自行用 VPN / Tailscale |
| 中继服务器 | 违背"本地优先、无服务器依赖" |
| 明文传输选项 | 即使在"可信网络"也不提供，避免误用 |
| 写入 / 同步 | 决策 D-21 明确只读；双向同步的冲突解决复杂度高 |

## 8. 用户体验流程

### 8.1 共享方

```
1. 设置 → 局域网共享 → 开启
2. 选择共享目录、权限、有效期
3. 显示：📡 正在共享 · 设备名「书房台式机」· 2 个目录
4. 有设备连接时显示通知
5. 随时可查看连接设备、访问日志，一键断开
```

### 8.2 浏览方

```
1. 侧栏「附近设备」自动显示局域网内的 omy 设备
2. 点击 → 首次需输入配对码（对方屏幕上显示）
3. 配对成功 → 浏览对方共享的文件
4. 用自己的密码解锁 → 能打开的文件正常显示名称和缩略图
   打不开的显示为 🔒 加密文件（当前密码无法打开）
5. 点击视频 → 直接播放，可任意 seek
```

### 8.3 UI 中的状态指示

远程文件在列表中带明确标记：

```
📁 书房台式机 › 工作资料
   ⚡ 📄 季度报告.docx      2.3 MB    🌐 远程
   ⚡ 🎬 演示视频.mp4      847 MB    🌐 远程
   🔒 未知文件            1.2 GB    🌐 远程 · 当前密码无法打开
```

网络状况差时显示缓冲指示，并在播放器上标注"🌐 远程播放"。
