## 3. 关键实测数据

### 3.1 文件尺寸与膨胀

| 输入 | 密文大小 | 固定开销 |
|---|---|---|
| 空文件 (0 B) | 672 B | 672 B |
| 1 字节 | 673 B | 672 B |
| 亚块 (255 B) | 927 B | 672 B |
| 恰好整块 (65,536 B) | 66,208 B | 672 B |

**最小文件 672 字节**（空文件 + 单密码 + 加密文件名）。固定开销恒定，不随文件增大而增长（除每块 16 B 的 AEAD tag）。

### 3.2 两级 KDF 性能（D-02 可行性的关键证据）

| 操作 | 耗时 |
|---|---|
| Argon2id (m=64 MiB, t=3, p=1) 单次 | **180 ms** |
| HKDF 单次 | **13.2 µs** |
| **比值** | **~13,700×** |
| 5 个密码派生 KEK（每会话一次） | 778 ms |
| **扫描 500 文件 × 5 密码** | **170 ms**（500/500 命中） |
| 推算 10,000 文件 | **~3.4 s** |
| 对照：每文件独立 Argon2 | **394 s**（慢 **2,324×**） |

> 若不采用两级 KDF，10,000 文件扫描需约 2.5 小时——功能根本无法使用。
> 这证明两级 KDF **不是优化，是可行性前提**（见 [12 号文档 DEC-02](../12-decision-log.md)）。

#### 3.2.1 Rust 实现实测（2026-08-29，release 构建）

上表为 Python 参考实现在开发机上的测量值。Rust 实现的实测数据如下，
**结论一致，但绝对值更快**——两级 KDF 的可行性得到独立复现：

| 操作 | Python 参考 | Rust release | 说明 |
|---|---:|---:|---|
| Argon2id (m=64 MiB, t=3, p=1) | 180 ms | **91.2 ms** | 同参数，Rust 约快 2× |
| HKDF-SHA256 单次 | 13.2 µs | **0.30 µs** | 10 万次取平均 |
| **比值** | ~13,700× | **~304,000×** | |
| 扫描 300 文件（KEK 已缓存） | — | **95 ms** | 0.315 ms/文件 |
| 推算 10,000 文件 | ~3.4 s | **~3.2 s** | 两者吻合 |

**正确性同时验证**：300 个文件中 100 个用当前密码加密、200 个用其它密码，
另混入 75 个非 omy 文件。扫描结果精确解锁 100 个，识别出全部 300 个 omy 文件，
噪音文件**零误判**。

> **关于「2.5 小时」的口径**：该数字对应 `10,000 文件 × 5 密码 × 180 ms`
> （即每个文件对每个密码都跑一次 Argon2）。若只算单密码则为 30 分钟。
> 两种口径下两级 KDF 的必要性都成立。
>
> **测量环境差异**：Argon2id 耗时强烈依赖内存带宽与 CPU，不同设备可相差数倍。
> 移动端通常显著慢于桌面端，这是 `MOBILE` 档位（m=32 MiB）存在的原因。
> 实现**不得**把任何具体耗时当作常量写入代码逻辑。

复现命令：

```bash
cargo run --release --example bench_scan -- 300
```

## 5. 验证过程中发现并修复的问题

> 这些是**真实发现的缺陷**，不是演示。它们也是本设计文档可信度的主要依据。

### 5.1 🐛 批量加密每文件重跑 Argon2

初版 `EncryptParams` 只接受 `passwords`，批量加密时每文件重跑一次 Argon2（180 ms × N）。

**修复**：增加 `keks` 字段接受预派生 KEK。同时这条成为生产实现的硬性要求（见 [09 号文档 §5.1](../09-cli-design.md)）。

### 5.2 🐛 文件名 padding 负填充（安全缺陷）

原公式 `bucket = (len // 64 + 1) * 64` 在 `len = 63` 时产生**负填充**——实际需要 `2 + 63 = 65` 字节，但桶只有 64，padded 长度越出边界变成 65。

**后果**：该长度的文件名反而**暴露自己的长度特征**，与 padding 的目的完全相反。这是安全缺陷而非单纯的逻辑错误。

**修复**：基于最终写入字节数计算 `need = 2 + len`；`bucket = ceil(need/64)*64`。

**修复后验证**：长度 0–199 及 250 / 300 的文件名落入 5 个桶，**同桶内 `header_len` 完全唯一**——无法从 header 长度反推文件名长度。

### 5.3 🐛 测试断言本身的方法学错误

这是我自己设错了阈值，属于"测试通过不代表测试正确"的典型情况。

**错误一 · 用字节覆盖率检测随机性**
原断言"slot 区字节覆盖率 > 85%"。但 384 字节样本对 256 种取值严重欠采样，理论期望覆盖率仅约 **77.7%**——即使数据完美随机也永远达不到 85%。
→ 改为与**同长度纯随机对照组**做统计检验。

**错误二 · 用固定阈值比较熵差**
原断言"真实 slot 段与填充段熵差 < 0.35"。但实测两段**纯随机**数据（144 B vs 240 B）的熵差中位数就有 **0.456**——短样本熵估计对长度极度敏感。
→ 改为与随机基线 p95 比较。

**教训**：对随机性/熵的断言必须用同分布对照组。拍脑袋定阈值的结果要么永远失败、要么永远通过，两种情况下测试都没有价值。

### 9.3 变异测试：9 项，其中一项真的抓出了断言不足

| 变异 | 模拟的真实错误 | 结果 |
|---|---|---|
| N1 纯文本消息被过滤 | **套用文件视图判据**（最核心的失效） | ⚠️ **首轮存活** → 补强后抓到 |
| N2 计数不随加载更新 | 数字变成谎言 | 抓到 BD8 |
| N3 加载中不禁用按钮 | 重复触发同一页 | 抓到 BD3 |
| N4 新内容插到顶部 | 顶飞用户的滚动位置 | 抓到 BD9 |
| N5 分组标题不粘顶 | 滚动后失去时间锚点 | 抓到 BA5 |
| N6 广播时把入口灰掉 | 分不清「不支持」与「没连上」 | 抓到 BE1 |
| N7 措辞改「暂未支持」 | 承诺一件不打算做的事 | 抓到 BE5 |
| N8 视频去掉时长角标 | 点开才知道多长 | 抓到 BB4 |
| N9 移动端去掉时间分组 | 只在桌面做适配 | 抓到 BF1 |

🔴 **N1 首轮存活，且这次是真的断言不足**（不是变异写错，也不是空操作）。
原因：`querySelectorAll` **照样数得到 `hidden` 的元素**，
于是把纯文本全部隐藏后，「带文件数 < 总数」「计数 == DOM 条数」仍然成立——
而界面上纯文本已经一条都看不见了，**正是退化成文件视图的样子**。

**教训不在于补了什么，而在于我本来就写过这条。** §9.5 的清单里明明白白有
「**『有没有』类断言要数可见元素，不要只数 DOM 节点个数**」，
写新断言时却没照着自己的清单做。修法：BC4 改为数**可见**条数，
并新增 BC5 直接断言「纯文本实测可见且与计数相符」。补强后复跑 N1 —— 抓到，还原全绿。

**这也说明变异测试不是走过场**：它证明的是**断言有效**，而不是产品正确。
本轮 41 项里有 2 项是被变异测试逼出来的。

### 9.4 一条误报，仍然是探针的错

| 误报 | 真实原因 |
|---|---|
| 「广播措辞含『加载失败』」 | 原文是「也**不是**加载失败」——**否定句**，恰恰是想要的措辞。我的断言粗暴禁了子串，没区分「说了这个词」和「说了不是这个词」 |

这是本任务**第四次**栽在按文字匹配上（前三次：匹配串与原型措辞不符、
被自己写的注释骗到、属性真实取值是 `mobile` 而非 `mob`）。
修法：只禁**肯定形式**——检查该词前三个字符内有没有「不是 / 并非」。

> 优先按结构属性定位。

### 9.5 复现方式

探针为一次性工具，验证完成后已移除（AGENTS.md：临时脚本不进仓库）。要点：

- 用真实浏览器 + CDP 回读 DOM 与 `getComputedStyle`，不读源码字符串；
- 定位**按结构属性**，并先确认属性的**真实取值**；
- 🔴 **「有没有」类断言必须数可见元素**（`getBoundingClientRect`），
  只数 DOM 节点会放过 `hidden` / 零尺寸的退化——本轮 N1 实测溜过一次；
- 文字类断言要考虑**否定句、注释、示例文本**，或干脆别用；
- 查「正文里有没有某种文本」时先排除 `pre` / `script` / `style`；
- **查可见性前先激活对应面板**，互斥面板里的元素默认都是 0x0；
- **显式设置状态而不是盲目推进**，否则多轮循环会互相污染；
- **颜色断言要让浏览器解析两边**再比；
- **动作型调用要容错**，否则一次崩溃会掩盖后面全部断言；
- 判「变异是否被抓到」要看**失败列表里有没有为它写的那条**，不能只看退出码
  （探针崩溃时 rc 同样非 0 却一条 `[FAIL` 都没有）；
- 还原源码后显式 `os.utime` 刷新 mtime，并**复跑确认恢复全绿**。
