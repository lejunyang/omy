## 3. 关键实测数据

### 3.1 文件尺寸与膨胀

| 输入 | 密文大小 | 固定开销 |
|---|---|---|
| 空文件 (0 B) | 672 B | 672 B |
| 1 字节 | 673 B | 672 B |
| 亚块 (255 B) | 927 B | 672 B |
| 恰好整块 (65,536 B) | 66,208 B | 672 B |

**最小文件 672 字节**（空文件 + 单密码 + 加密文件名）。固定开销恒定，不随文件增大而增长（除每块 16 B 的 AEAD tag）。

### 3.2 两级 KDF 性能（D-02 可行性的关键证据）

| 操作 | 耗时 |
|---|---|
| Argon2id (m=64 MiB, t=3, p=1) 单次 | **180 ms** |
| HKDF 单次 | **13.2 µs** |
| **比值** | **~13,700×** |
| 5 个密码派生 KEK（每会话一次） | 778 ms |
| **扫描 500 文件 × 5 密码** | **170 ms**（500/500 命中） |
| 推算 10,000 文件 | **~3.4 s** |
| 对照：每文件独立 Argon2 | **394 s**（慢 **2,324×**） |

> 若不采用两级 KDF，10,000 文件扫描需约 2.5 小时——功能根本无法使用。
> 这证明两级 KDF **不是优化，是可行性前提**（见 [12 号文档 DEC-02](../12-decision-log.md)）。

#### 3.2.1 Rust 实现实测（2026-08-29，release 构建）

上表为 Python 参考实现在开发机上的测量值。Rust 实现的实测数据如下，
**结论一致，但绝对值更快**——两级 KDF 的可行性得到独立复现：

| 操作 | Python 参考 | Rust release | 说明 |
|---|---:|---:|---|
| Argon2id (m=64 MiB, t=3, p=1) | 180 ms | **91.2 ms** | 同参数，Rust 约快 2× |
| HKDF-SHA256 单次 | 13.2 µs | **0.30 µs** | 10 万次取平均 |
| **比值** | ~13,700× | **~304,000×** | |
| 扫描 300 文件（KEK 已缓存） | — | **95 ms** | 0.315 ms/文件 |
| 推算 10,000 文件 | ~3.4 s | **~3.2 s** | 两者吻合 |

**正确性同时验证**：300 个文件中 100 个用当前密码加密、200 个用其它密码，
另混入 75 个非 omy 文件。扫描结果精确解锁 100 个，识别出全部 300 个 omy 文件，
噪音文件**零误判**。

> **关于「2.5 小时」的口径**：该数字对应 `10,000 文件 × 5 密码 × 180 ms`
> （即每个文件对每个密码都跑一次 Argon2）。若只算单密码则为 30 分钟。
> 两种口径下两级 KDF 的必要性都成立。
>
> **测量环境差异**：Argon2id 耗时强烈依赖内存带宽与 CPU，不同设备可相差数倍。
> 移动端通常显著慢于桌面端，这是 `MOBILE` 档位（m=32 MiB）存在的原因。
> 实现**不得**把任何具体耗时当作常量写入代码逻辑。

复现命令：

```bash
cargo run --release --example bench_scan -- 300
```

## 5. 验证过程中发现并修复的问题

> 这些是**真实发现的缺陷**，不是演示。它们也是本设计文档可信度的主要依据。

### 5.1 🐛 批量加密每文件重跑 Argon2

初版 `EncryptParams` 只接受 `passwords`，批量加密时每文件重跑一次 Argon2（180 ms × N）。

**修复**：增加 `keks` 字段接受预派生 KEK。同时这条成为生产实现的硬性要求（见 [09 号文档 §5.1](../09-cli-design.md)）。

### 5.2 🐛 文件名 padding 负填充（安全缺陷）

原公式 `bucket = (len // 64 + 1) * 64` 在 `len = 63` 时产生**负填充**——实际需要 `2 + 63 = 65` 字节，但桶只有 64，padded 长度越出边界变成 65。

**后果**：该长度的文件名反而**暴露自己的长度特征**，与 padding 的目的完全相反。这是安全缺陷而非单纯的逻辑错误。

**修复**：基于最终写入字节数计算 `need = 2 + len`；`bucket = ceil(need/64)*64`。

**修复后验证**：长度 0–199 及 250 / 300 的文件名落入 5 个桶，**同桶内 `header_len` 完全唯一**——无法从 header 长度反推文件名长度。

### 5.3 🐛 测试断言本身的方法学错误

这是我自己设错了阈值，属于"测试通过不代表测试正确"的典型情况。

**错误一 · 用字节覆盖率检测随机性**
原断言"slot 区字节覆盖率 > 85%"。但 384 字节样本对 256 种取值严重欠采样，理论期望覆盖率仅约 **77.7%**——即使数据完美随机也永远达不到 85%。
→ 改为与**同长度纯随机对照组**做统计检验。

**错误二 · 用固定阈值比较熵差**
原断言"真实 slot 段与填充段熵差 < 0.35"。但实测两段**纯随机**数据（144 B vs 240 B）的熵差中位数就有 **0.456**——短样本熵估计对长度极度敏感。
→ 改为与随机基线 p95 比较。

**教训**：对随机性/熵的断言必须用同分布对照组。拍脑袋定阈值的结果要么永远失败、要么永远通过，两种情况下测试都没有价值。

### 9.1 本轮为什么是「重写」而不是「追加」

四处实质变更让旧套件的一部分直接失效：

| 变更 | 对旧断言的影响 |
|---|---|
| **tdata 入口按用户要求加回** | 旧 **Q 组 4 条整组反向**——它当时锁的正是「界面上**没有** tdata 入口」 |

防止 tdata 入口被**悄悄**加回来；本轮用户明确要求恢复，所以它们被**反向重写**
为「入口存在且五条前提都落到了界面上」（U 组）。依据记录在此，

### 9.3 三条误报，全部是探针自己的错

本轮探针报了 3 次失败，逐条核实后**全部是探针缺陷，产品无问题**。
记下来是因为它们属于同一类错误，下次还会犯：

| 误报 | 真实原因 | 证据 |
|---|---|---|
| 「说明写清总数会消失」 | 我去匹配「取完返回 None」，而原型写的是「**取完反而返回空**」 | 打印正文后一眼看到 |
| 两条「新组件不可见」 | `#codechan` 在 `data-ps="2"` 里、tdata 组件在 `data-auth="tdata"` 里，**默认都隐藏**；不先激活面板就查，必然得到 0x0 | 激活后实测 659x82 / 659x24 / 659x80 / 420x34，颜色对比正常 |
| 「light 主题下不可见」（dark 却通过） | **状态跨轮累积**：探针每轮盲点一次「下一步」，第二轮把子步从 2 推到了 3 | 打印子步：第 1 次点→`2`、`659x82`；第 2 次点→`3`、`0x0`；显式退回→又是 `659x82` |

**第三条最值得记。** 它的特征是**非对称失败**——同一段代码，dark 过了 light 没过。
凡是出现这种不对称，先怀疑状态而不是主题。修法也一致：探针要**显式设置状态**
（循环点到目标子步为止），而不是依赖「当前恰好在哪一步」。
依赖顺序的断言迟早会因为插入新用例而失真。

这三条都遵循了 AGENTS.md 那一条：**实测失败时先怀疑脚本、打印真实字段值，
再改产品**。三次全部止步于探针，一次都没有误改产品。

### 9.4 两个仍然有效的验证陷阱

**① 调试端口被别的进程占着，跑的一直是旧页面。**
「重启浏览器」只杀启动器 PID，真正持有端口的子进程还活着，于是每次都连到
**同一个从未重载的页面**，状态跨次累积。修法：按**端口**找到真正的占用者再杀
（`Get-NetTCPConnection -LocalPort ... | Stop-Process -Id $_.OwningProcess`），
启动前断言端口已释放，并让探针自己 `Page.reload`。

**② `UnicodeEncodeError` 把目标文件截成 0 字节。**
补丁脚本里含写成代理对形式的 emoji，`f.write()` 在**打开文件并清空之后**才抛错，
原型变成 0 字节——错误信息只提「surrogates not allowed」，看不出文件已被毁。
此后所有补丁脚本一律**不写 `\uXXXX` 转义、只写字面量**，
并且**写完回读校验**（长度、是否以 `</html>` 结尾、严格 UTF-8 能否解码）。

**③ 探针崩溃会把任何变异都显示成「抓到」。** 页面脚本被破坏后所有交互失效，
探针在一个**无关**动作上崩溃退出，rc 非 0 但**一条 `[FAIL` 都没有**。
判据不能只看 rc，要看**失败列表里有没有为这条要求写的那条断言**。
所有动作型调用都包了容错函数，让「动作执行不了」本身落成一条可读的失败记录。

### 9.5 复现方式

探针为一次性工具，验证完成后已移除，不随文档交付
（AGENTS.md：临时脚本不进仓库）。如需复现或重建全量套件，要点是：

- 用真实浏览器 + CDP 回读 DOM 与 `getComputedStyle`，不读源码字符串；
- 定位**按结构属性**（`data-*` / `id` / class），**不按文字**——
  emoji 的代理对与变体选择符会让文字匹配不可靠，中文标签一改就失配；
- **查可见性前先激活对应面板**（§9.3 第二条），互斥面板里的元素默认都是 0x0；
- **显式设置状态而不是盲目推进**（§9.3 第三条），否则多轮循环会互相污染；
- **颜色断言要让浏览器解析两边**再比，不要拿 `rgb()` 去比 `#rrggbb`；
- **「有没有」类断言要数可见元素**，不要只数 DOM 节点个数；
- **动作型调用要容错**，否则一次崩溃会掩盖后面全部断言；
- 每次运行前确认调试端口无残留占用，并由探针自己 reload；
- 每条断言都要能说出「不这样会怎样」，并用变异测试验证它真的会失败——
  且要确认变异**不是空操作**、失败**是定向命中**的。
