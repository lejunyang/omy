## 3. 关键实测数据

### 3.1 文件尺寸与膨胀

| 输入 | 密文大小 | 固定开销 |
|---|---|---|
| 空文件 (0 B) | 672 B | 672 B |
| 1 字节 | 673 B | 672 B |
| 亚块 (255 B) | 927 B | 672 B |
| 恰好整块 (65,536 B) | 66,208 B | 672 B |

**最小文件 672 字节**（空文件 + 单密码 + 加密文件名）。固定开销恒定，不随文件增大而增长（除每块 16 B 的 AEAD tag）。

### 3.2 两级 KDF 性能（D-02 可行性的关键证据）

| 操作 | 耗时 |
|---|---|
| Argon2id (m=64 MiB, t=3, p=1) 单次 | **180 ms** |
| HKDF 单次 | **13.2 µs** |
| **比值** | **~13,700×** |
| 5 个密码派生 KEK（每会话一次） | 778 ms |
| **扫描 500 文件 × 5 密码** | **170 ms**（500/500 命中） |
| 推算 10,000 文件 | **~3.4 s** |
| 对照：每文件独立 Argon2 | **394 s**（慢 **2,324×**） |

> 若不采用两级 KDF，10,000 文件扫描需约 2.5 小时——功能根本无法使用。
> 这证明两级 KDF **不是优化，是可行性前提**（见 [12 号文档 DEC-02](../12-decision-log.md)）。

### 3.3 可否认性（D-02）

| 检验项 | 实测 |
|---|---|
| 1 密码 vs 3 密码文件大小 | **772 B vs 772 B**（完全相同） |
| slot 区熵 | **7.455 bits/byte** |
| 纯随机基线区间 | **[7.350, 7.557]** → 落在区间内 ✅ |
| 真实 slot 与随机填充的熵差 | **0.471** |
| 随机基线 p95 | **0.590** → 未超出 ✅ |

无法从文件本身判断实际配置了几个密码。

> **边界说明**：这抵抗的是静态文件分析，**不**抵抗时间戳关联、备份历史对比、内存取证。详见 [12 号文档 DEC-13](../12-decision-log.md)。

### 3.4 块大小对压缩率的影响（D-09）

2 MB 高重复语料，zstd-3：

| 块大小 | 压缩后 | 占原始 |
|---|---|---|
| 64 KiB | 133,515 B | 6.52% |
| 256 KiB | 34,004 B | 1.66% |
| 1 MiB | 9,158 B | 0.45% |
| 4 MiB | 5,017 B | 0.24% |

**4 MiB 块比 64 KiB 小 96.2%**，证实了用户「提高块大小可以解决分块压缩收益小的问题」的判断。

### 3.5 缩略图带来的列表页收益（D-10）

| 项 | 大小 |
|---|---|
| header（含加密缩略图） | 8,771 B |
| 整个文件 | 58,787 B |

列表页只需读 header → **读取量减少 85%**，无需触碰载荷区。

## 4. 交叉验证（98 项）

`verify_spec.py` 做两件事，目的是**用不同于生成路径的方式回读**：

### 4.1 文档偏移表 ↔ 实现字节布局

用正则解析 [02 号文档](../02-file-format-spec.md) 中的偏移表，与参考实现产生的实际字节逐字段比对：

- Fixed Header 全部字段的偏移与长度
- MAGIC = `43 56 41 55 4C 54 01 00`
- SHARD_MAGIC = `"CVSHARD" + 0x01`
- slot 区起止（96 → 480）
- `header_len = 96 + 384 + tlv_len + 32`
- 字节序（全小端，唯一例外：nonce 中块序号为 u32be）
- O(1) 偏移公式 `ct_offset(i) = header_len + i * (chunk_size + 16)`

### 4.2 独立解密测试向量

不复用加密时的中间状态，从 `appendix/test-vectors.json` 记录的密码出发完整重做一遍：

```
[OK] v1 可用文档记录的密码解锁
[OK] v1 KEK 与记录一致
[OK] v1 FEK 与记录一致
[OK] v1 命中 slot 索引一致
[OK] v1 header MAC 有效
[OK] v1 明文还原正确
[OK] v1 文件名还原正确
```

5 组测试向量的 magic、size 字段与 hex 长度一致性、BLAKE2b-256 哈希均已校验。

## 5. 验证过程中发现并修复的问题

> 这些是**真实发现的缺陷**，不是演示。它们也是本设计文档可信度的主要依据。

### 5.1 🐛 批量加密每文件重跑 Argon2

初版 `EncryptParams` 只接受 `passwords`，批量加密时每文件重跑一次 Argon2（180 ms × N）。

**修复**：增加 `keks` 字段接受预派生 KEK。同时这条成为生产实现的硬性要求（见 [09 号文档 §5.1](../09-cli-design.md)）。

### 5.2 🐛 文件名 padding 负填充（安全缺陷）

原公式 `bucket = (len // 64 + 1) * 64` 在 `len = 63` 时产生**负填充**——实际需要 `2 + 63 = 65` 字节，但桶只有 64，padded 长度越出边界变成 65。

**后果**：该长度的文件名反而**暴露自己的长度特征**，与 padding 的目的完全相反。这是安全缺陷而非单纯的逻辑错误。

**修复**：基于最终写入字节数计算 `need = 2 + len`；`bucket = ceil(need/64)*64`。

**修复后验证**：长度 0–199 及 250 / 300 的文件名落入 5 个桶，**同桶内 `header_len` 完全唯一**——无法从 header 长度反推文件名长度。

### 5.3 🐛 测试断言本身的方法学错误

这是我自己设错了阈值，属于"测试通过不代表测试正确"的典型情况。

**错误一 · 用字节覆盖率检测随机性**
原断言"slot 区字节覆盖率 > 85%"。但 384 字节样本对 256 种取值严重欠采样，理论期望覆盖率仅约 **77.7%**——即使数据完美随机也永远达不到 85%。
→ 改为与**同长度纯随机对照组**做统计检验。

**错误二 · 用固定阈值比较熵差**
原断言"真实 slot 段与填充段熵差 < 0.35"。但实测两段**纯随机**数据（144 B vs 240 B）的熵差中位数就有 **0.456**——短样本熵估计对长度极度敏感。
→ 改为与随机基线 p95 比较。

**教训**：对随机性/熵的断言必须用同分布对照组。拍脑袋定阈值的结果要么永远失败、要么永远通过，两种情况下测试都没有价值。

## 6. 复现方式

```bash
cd cryptovault-design

# 参考实现自测（68 项，含 Argon2 基准，约需数十秒）
python3 reference/test_cvlt.py

# 文档 ↔ 实现交叉验证（98 项）
python3 verify_spec.py

# 重新生成测试向量（修改 cvlt_ref.py 后必须执行）
python3 reference/gen_vectors.py
```

**依赖**：`pip3 install cryptography argon2-cffi zstandard`

> ⚠️ 修改 `reference/cvlt_ref.py` 后必须重跑 `gen_vectors.py` 重新生成向量（哈希会变），再重跑 `test_cvlt.py` 与 `verify_spec.py` 回归。padding 修复时已走过该流程。
