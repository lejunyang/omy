# 原型 vs 实现 全量对照清单（Telegram 远程位置）

> 对照对象：`docs/research/appendix/telegram-remote-prototype.html`（约 3960 行）
> 与 omy 当前实现。
>
> **核对方式：对着实际运行的 GUI 逐项操作核对，不是读实现代码推断。**
> 这一条不是形式要求——此前踩过：`PlaceBrowser` 里早就有 `@contextmenu`
> 和缩略图渲染代码，却被 `activatable()` 恒返回 false 整个废掉。
> **代码存在 ≠ 功能可用**，基于读代码产出的清单会系统性地偏乐观。
>
> **口径**：原型全绿不能替实现背书，实现跑通也不代表原型描述的交互都做了。
> 这份清单的价值正在于把这两件事分开。

## 状态取值

| 记号 | 含义 |
|---|---|
| ✅ 已验证 | 已实现，且本轮对着运行中的 GUI 实测过（括号里注明方式） |
| 🟡 未验证 | 代码路径存在，但没有端到端实测过，不保证可用 |
| ❌ 未实现 | 界面上没有 |
| ⚪ 不适用 | 有意不做，或本环境无样本可测 |

验证方式缩写：**真机** = 连真实 Telegram 账号实测；**GUI** = CDP 驱动
真实界面操作；**单测** = `cargo test`；**移动** = 390×844 移动视口 + 触摸模拟。

## 一、连接向导与登录

| 原型项 | 状态 | 说明 |
|---|---|---|
| 风险告知步骤（第三方客户端风险、勾选后才能继续） | ✅ 已验证（GUI） | **只拦首次登录**：判据是本机还没有任何 Telegram 位置，已有账号再加一个不重复拦。不用 localStorage 标记——换机器或清数据后就不再提示，而那恰恰是一次真正的首次登录。实测本机已有 p3 时不出现 |
| 内置 api_id 说明（「当前使用 omy 内置的 API 凭据」） | ✅ 已验证（GUI） | 登录对话框里一行状态，用自己那对时显示「当前使用你自己的 api_id（N）」 |
| 改用自己的 api_id / api_hash（含格式校验、保存并重连、恢复内置值） | ✅ 已验证（GUI） | 校验复用后端既有的 `AppId::from_config`，不另写一套规则。实测乱填当场报错且**不落盘**、合法值真的写进 config.toml、恢复内置真的清掉。api_hash 不回传给界面（它是凭据）。这是内置 api_id 被限流时的唯一自救入口 |
| `API_ID_PUBLISHED_FLOOD` 错误态引导去填自己的 api_id | 🟡 已实现未验证 | 入口已经常驻在登录对话框里（不再依赖错误态才出现）。**该错误本身无法人为构造**——它取决于 Telegram 侧对内置 api_id 的阈值 |
| 代理地址输入 | ✅ 已验证（GUI） | 登录对话框内有输入框与说明 |
| 代理 scheme 不支持时「一键改为 socks5://」 | ✅ 已验证（GUI） | 填 `http://` 时出现提示与按钮，点击后输入框真的改写成 `socks5://`、提示随之消失。此前是**静默**按同端口 SOCKS5 尝试——能用，但用户不知道真正生效的是什么 |
| 「从系统设置读取」代理 | ✅ 已验证（GUI） | 登录对话框里的按钮，点后填回系统代理并自动重新自检。后端 `detect_system_proxy` 读注册表，结果过 `normalize` 保证是 `socks5://` |
| 连接检查（正在检查 / 重新检查） | ✅ 已验证（真机 + GUI） | 登录**之前**自检，三种结果分开报：`ok`（带耗时与走的是直连还是代理）/ `bad_proxy`（地址不合法，重试无用）/ `no_route`（连不上）。实测本机三种都能真实触发：无代理 6.0s 超时判 no_route、经 socks5 判 ok、`ftp://` 判 bad_proxy。只做 TCP 不做 MTProto 握手——握手失败还可能是 api_id 问题，混在一起就违背了「先把归因定下来」 |
| 扫码登录入口 | ✅ 已验证（真机） | 真实账号扫码登录成功，session 落盘 3097 B |
| 二维码自动刷新（过期后换图且界面可见） | ✅ 已验证（单测 + 真机） | `AUTH_TOKEN_EXPIRED` → 重新导出；`refresh_index` 让界面能看出换了图 |
| 二维码倒计时 | ✅ 已验证（单测） | 显示服务端完整寿命（约 30 秒）；提前 3 秒换图是内部行为、不进显示值 |
| 二维码尺寸是否可扫 | ⚪ 待用户真机确认 | 未真正发起扫码以免打扰账号 |
| 2FA 云密码（服务端要求时才出现的动态子步） | ✅ 已验证（真机） | 真实账号走到过这一步 |
| 验证码登录（数字 / 单词 / 短句三种形态） | ❌ 未实现 | **有意不做**：本期只做扫码与 tdata。原型 `#codeDigits` `#codeWord` `#codePhrase` 对应的是手机号登录那条路 |
| 验证码送达渠道说明（发到应用内还是短信） | ❌ 未实现 | 依赖上一项 |
| `FLOOD_WAIT` 限流等待（倒计时、不给重试按钮） | 🟡 未验证 | 后端能识别并带出秒数（单测覆盖），但没有真机撞过限流来看界面表现 |
| 软键盘弹出时输入框是否被遮挡 | ⚪ 待用户真机确认 | CDP 无法弹出软键盘 |

## 八、错误态

| 原型项 | 状态 | 说明 |
|---|---|---|
| `FLOOD_WAIT` 限流等待条 | ⚪ 有意不测 | **不是没验，是决定不验**：要真的触发就得把账号打进限流，而这是用户**唯一**的测试账号，且他此前已被限流堵过一次（那次收不到验证码就是它）。为验一个错误态再把他堵住不值得。后端能识别并带出秒数，有单测覆盖 |
| session 失效 / 损坏 | ✅ 已验证（真机） | 改坏 session 密文后报 `tg_session_unreadable`「读取登录态失败：登录态解不开，需要重新登录」，与「网络连不上」是不同错误码；位置仍留在侧栏而不是消失。**验前备份、验后还原并复查账号可用** |
| `API_ID_PUBLISHED_FLOOD` → 引导填自己 api_id | ❌ 未实现 | 依赖 api_id 界面。**且无法人为构造**：这个错误只有在内置 api_id 被大量第三方客户端共用、触发 Telegram 侧阈值时才出现，不受本地控制 |
| 代理 scheme 不支持 | ✅ 已验证（真机） | `ftp://` 报 `tg_bad_proxy`「不支持的代理类型 ftp，请使用 socks5（或能同时提供 socks5 的混合端口）」。`http://` **不报错**——按设计自动改用同端口 SOCKS5（§7 的归一化）。原型那个「一键改为 socks5://」按钮仍未实现，当前是静默自动转换 |
| 网络不可达 | ✅ 已验证（真机） | 代理指向 `socks5://127.0.0.1:1`，5.1 秒后报 `tg_connect_failed`「连接失败：request error: Proxy server unreachable」，不是静默卡住 |
| 上述错误码在界面上是可读文案而非原始码 | ✅ 已验证（源码核对） | `tg_bad_proxy` / `tg_no_session` / `tg_session_unreadable` / `tg_connect_failed` 在中英两份 `*.errors.json` 里都有对应文案 |
| `file_reference` 过期刷新 | ❌ 未实测 | 仍在未实测清单里（见 §11） |

### 关于「未验证」与「不测」的区别

清单里刻意把三种情况分开写，它们对后来者的意义不同：

- **🟡 未验证**：能验，只是这一轮没排上。后来者可以直接去验。
- **⚪ 有意不测**：能验，但代价不值得（如 `FLOOD_WAIT` 会堵住用户唯一的
  账号）。理由写在条目里，后来者可以重新权衡，而不必重新发现这个代价。
- **无法构造**：不在本地控制范围内（如 `API_ID_PUBLISHED_FLOOD` 取决于
  Telegram 侧阈值）。写清这一点，免得有人反复尝试。
