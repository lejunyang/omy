# 原型 vs 实现 全量对照清单（Telegram 远程位置）

> 对照对象：`docs/research/appendix/telegram-remote-prototype.html`（约 3960 行）
> 与 omy 当前实现。
>
> **核对方式：对着实际运行的 GUI 逐项操作核对，不是读实现代码推断。**
> 这一条不是形式要求——此前踩过：`PlaceBrowser` 里早就有 `@contextmenu`
> 和缩略图渲染代码，却被 `activatable()` 恒返回 false 整个废掉。
> **代码存在 ≠ 功能可用**，基于读代码产出的清单会系统性地偏乐观。
>
> **口径**：原型全绿不能替实现背书，实现跑通也不代表原型描述的交互都做了。
> 这份清单的价值正在于把这两件事分开。

## 状态取值

| 记号 | 含义 |
|---|---|
| ✅ 已验证 | 已实现，且本轮对着运行中的 GUI 实测过（括号里注明方式） |
| 🟡 未验证 | 代码路径存在，但没有端到端实测过，不保证可用 |
| ❌ 未实现 | 界面上没有 |
| ⚪ 不适用 | 有意不做，或本环境无样本可测 |

验证方式缩写：**真机** = 连真实 Telegram 账号实测；**GUI** = CDP 驱动
真实界面操作；**单测** = `cargo test`；**移动** = 390×844 移动视口 + 触摸模拟。

| 客户端正在运行的检测与「请从托盘退出」提示 | 🟡 未验证 | 后端 `telegram_tdata_probe` 返回 `client_running`，界面是否据此提示未实测 |
| 多账号选择（并排除 `tupdates\temp\tdata` 幽灵项） | 🟡 未验证 | 后端已实现排除逻辑（单测覆盖），界面选择器未实测 |
| 同一账号登录去重（扫码 / 手机号 / tdata 三路） | ✅ 已验证（真机 + 单测） | 判据是服务端 user id（昵称会重会改，只有它唯一）。命中已有账号时不新建、跳到已有位置并提示「该账号已添加」、用新登录态覆盖旧连接与 session、不留孤儿。**真机实测**：p4（Joh）的 tdata 重新导入返回 `{id:"p4",duplicate:true}`、位置数不变（2→2）、无 pending 孤儿 session；p3/p4 两个不同账号各自补到不同 user id 未被误并。老配置无 user_id 字段时反序列化不崩、进入时由 `ensure_connected` 补取。6 个单测覆盖命中 / 排除 / 不误并 / 换连接保 id 与名字 / 持久化往返 / 老配置迁移 |
| 对话/文件懒加载对齐官方（DEC-26） | ✅ 已验证（真机计时） | 对话列表头像改并发下载（8 路）+ 按 chat id 复用缓存 + **列表先返回、头像后台补齐**（复用 remote-entry 事件通道）：72 对话冷启动 48.7s→3.2s 出列表、头像随后逐张补上（DOM 带头像卡片 2→37 增长、总数恒 72 不跳位）、二次 0.95s。文件首页 `DEFAULT_MESSAGE_PAGE` 100→15，进对话 约 470ms。进对话不再触发全量对话刷新（`list_more` 去冗余 refresh）。缓存优先渲染真机验证：进→退→再进第二次 0.0s 即出 72 张缓存卡片、无占屏 ⏳、只有顶部轻量 refreshing 提示（D+F）。缓存标识真机验证：pin clip.mp4 后 DOM 出现 📌、`stat.pinned=true`、缓存用量可查（E）。验完 unpin 还原、`list_pinned` 空、无残留 |
| 本地密码（passcode）输入 | 🟡 已实现未验证 | 界面有（`td-passwrap`），由后端返回 `tg_tdata_need_passcode` 时展开，密码错时保持可见以便重输。**本账号的 tdata 没有设本地密码，这条分支没有真实样本可触发** |
| 本地密码与云密码的文案区分 | ✅ 已验证（源码核对） | `tg.tdata_passcode_hint` 明说「这是你为 Telegram Desktop 这个程序设的本地密码（打开客户端时要输的那个）。不是两步验证的云密码，也不是短信验证码」。两者都叫「密码」，不区分的话用户会把云密码填进来反复被拒 |
| 「导入后同时登出桌面端」选项 | ⚪ 有意不做（协议上做不到） | 导入 tdata **不是复制一份独立登录态，而是共用同一份 auth key**（§4.3 / §12.3.4）。`auth.logOut` 作废的正是当前这份 key，而 omy 用的就是同一份——在导入后的连接上调它，**不是「登出桌面端」，是两边一起没了**。<br>要做到「只登出桌面端」，得先用这份 key 换一份属于 omy 的新 authorization 再作废旧的，那是另一条登录路径（tdl 走的即是此路），不是加一个勾选框的事。<br>**代替做法**：把共用关系如实说清。原来的告知只讲了一个方向（桌面端登出 → omy 失效），现补成「任一边登出，两边都会失效，也因此没有『只登出桌面端』这个选项」——用户看到原型里有这个勾选、产品里没有时，能知道为什么 |
| 共用同一份会话的警告 | ✅ 已验证（GUI） | 界面有「桌面端登出时 omy 会一并失效」 |
| 导入并连接 | ✅ 已验证（真机） | 真实 tdata 样本解析出 4 把 auth key，服务端认 |

### 关于「未验证」与「不测」的区别

清单里刻意把三种情况分开写，它们对后来者的意义不同：

- **🟡 未验证**：能验，只是这一轮没排上。后来者可以直接去验。
- **⚪ 有意不测**：能验，但代价不值得（如 `FLOOD_WAIT` 会堵住用户唯一的
  账号）。理由写在条目里，后来者可以重新权衡，而不必重新发现这个代价。
- **无法构造**：不在本地控制范围内（如 `API_ID_PUBLISHED_FLOOD` 取决于
  Telegram 侧阈值）。写清这一点，免得有人反复尝试。
