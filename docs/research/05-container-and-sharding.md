# 05 · 文件夹加密与分片

## 1. 两种文件夹模式（决策 D-05：都要）

### 1.1 对比

| 维度 | **模式 A：容器化** | **模式 B：树形** |
|---|---|---|
| 形态 | 整个文件夹 → **单个** `.omy` | 每个文件单独加密，目录名也加密 |
| 目录结构 | ✅ **完全隐藏** | ⚠️ 泄露文件数量、大小分布、树形深度 |
| 增量修改 | ❌ 改一个文件要重写整个容器 | ✅ 只改单个文件 |
| 单文件分享 | ❌ 必须整包给出 | ✅ 可单独发送某个文件 |
| 云盘同步 | ❌ 每次全量重传 | ✅ 增量同步友好 |
| 单文件预览 | ✅（容器内寻址） | ✅ |
| 损坏影响面 | ⚠️ 头部损坏 = 全部丢失 | ✅ 只影响单个文件 |
| 类比 | 7-Zip 加密压缩包 | Cryptomator |
| **适用** | 归档、打包分享、一次性备份 | 日常使用的加密盘、云盘同步 |

### 1.2 UI 中的呈现

用户加密文件夹时必须明确选择：

```
📁 加密文件夹「工作资料」（1,247 个文件，3.2 GB）

  ◉ 打包成单个加密文件
     完全隐藏目录结构，适合归档和分享
     ⚠️ 修改任一文件需重写整包

  ○ 逐个加密（保持目录结构）
     支持增量修改和云盘同步
     ⚠️ 文件数量和大小分布可被外部观察到
```

## 2. 模式 A：容器化

### 2.1 结构

容器就是一个普通的 `.omy` 文件，`flags` 置位 `CONTAINER`，载荷内部是一个**迷你文件系统**：

```
┌──────────────────────────────────┐
│  标准 .omy header               │
│    flags |= CONTAINER            │
│    TLV_FOLDER_INDEX (CRITICAL+ENC)│  ← 目录索引
├──────────────────────────────────┤
│  载荷（分块 AEAD 加密）           │
│    ├── entry[0] 的字节            │
│    ├── entry[1] 的字节            │
│    ├── ...                        │
└──────────────────────────────────┘
```

### 2.2 目录索引格式

`TLV_FOLDER_INDEX` 的明文内容（MessagePack 或 CBOR 编码，此处以 JSON 示意）：

```json
{
  "version": 1,
  "root": "工作资料",
  "entries": [
    {
      "path": ["文档", "季度报告.docx"],
      "type": "file",
      "offset": 0,
      "size": 2451234,
      "blake2b256": "3f8a...",
      "meta": {"mtime": 1756425600, "mode": 33188}
    },
    {
      "path": ["文档", "草稿"],
      "type": "dir",
      "meta": {"mtime": 1756339200, "mode": 16877}
    },
    {
      "path": ["链接.txt"],
      "type": "symlink",
      "target": "文档/季度报告.docx",
      "meta": {"mtime": 1756425600}
    }
  ]
}
```

**关键设计**：
- `path` 用**数组**而非字符串拼接 → 天然规避路径分隔符差异和路径注入
- `offset` 是在**明文载荷流**中的偏移，与分块 AEAD 的寻址正交
- 空目录必须显式记录（`type: "dir"`），否则会丢失

### 2.3 容器内单文件预览

这是容器模式的关键能力——**不需要解开整个容器**：

```
播放容器内的 movie.mp4
  → 查 FOLDER_INDEX 得到 offset=1073741824, size=524288000
  → 播放器请求 Range: bytes=1000000-1065535（相对该文件）
  → 换算成容器内明文偏移：1073741824 + 1000000
  → 走标准分块 AEAD 寻址，只解密涉及的块
```

**与单文件模式完全复用同一套 Range 逻辑**，只是多了一层偏移基址。

### 2.4 大容器的索引优化

索引本身在 TLV 区，全部载入内存。对超大文件夹：

| 文件数 | 索引大小（估算） | 处理 |
|---|---|---|
| 1,000 | ~100 KB | 直接载入 |
| 10,000 | ~1 MB | 直接载入 |
| 100,000 | ~10 MB | ⚠️ 移动端需注意；考虑分块索引 |

超过阈值（建议 50,000 文件）时，UI 应建议改用模式 B。

## 3. 模式 B：树形

### 3.1 磁盘布局

```
明文原始结构：              加密后：
工作资料/                   MFZWIZLTOQ.omy/          ← 目录名也加密
├── 文档/                   ├── NBSWY3DPFQ.omy/
│   ├── 报告.docx           │   ├── ONXW2ZLUNBSGK.omy
│   └── 草稿.txt            │   └── MJQXGZLDN5XA.omy
└── 照片/                   └── PB2GK3TUN5XA.omy/
    └── IMG_001.heic            └── L5XG64TFMQXGG.omy
```

### 3.2 加密目录名的编码

**必须用 base32（RFC 4648），不能用 base64**：

| 问题 | base64 | **base32** |
|---|---|---|
| 含 `/` 字符 | ⚠️ 是（需替换） | ✅ 否 |
| 大小写敏感 | ⚠️ 是 —— **Windows/APFS 默认大小写不敏感，会冲突** | ✅ 全大写，无冲突 |
| 长度膨胀 | 1.33× | 1.6× |

**长度限制处理**：
- 多数文件系统单个组件上限 **255 字节**
- base32 膨胀 1.6× → 原始名上限约 150 字节
- 超长名称：截断 + 追加哈希后缀，完整名存入该文件自己的 `TLV_FILENAME`

```
超长文件名 → BASE32_PREFIX_120CHARS + "~" + BASE32(hash[0..6]) + ".omy"
```

- Windows 完整路径 260 字符限制：建议启用长路径支持，或提示用户缩短目录层级

### 3.3 目录名加密的密钥

目录名不属于任何单个文件，用 **vault 级别的密钥**派生：

```
dirname_key = HKDF(KEK, salt=vault_salt, info="omy/v1/dirname")
密文目录名   = base32(AEAD(dirname_key, nonce=随机(12B), 目录名))
              nonce 前置存储在密文中
```

⚠️ **注意**：这意味着目录名的可见性绑定 vault 密码，而非单个文件的 slot。在多密码场景下，能解开 vault 的任一密码都能看到目录结构。

### 3.4 泄露的元数据

模式 B 天然泄露（威胁模型 N6 已声明）：

| 可被观察 | 缓解手段 |
|---|---|
| 文件总数 | 可选：插入诱饵文件 |
| 每个文件的大致大小 | 可选：`SIZE_PADDED` 填充到桶 |
| 目录树的深度和分支结构 | 无（这是模式 B 的固有代价） |
| 文件的修改时间 | 可选：`META_NORMALIZED` |

**UI 必须告知**："逐个加密模式下，别人能看到你有多少文件、每个文件多大、目录有几层，但看不到文件名和内容。"

## 4. 元数据保留（决策 D-15、N3 认可的方案）

### 4.1 保存策略

**保存全部元数据到加密索引，解压时按目标平台能力尽力还原，不支持的项明确报告给用户**（而非静默丢弃）。

### 4.2 元数据项与跨平台问题

| 元数据 | 存储 | 跨平台问题 | 还原策略 |
|---|---|---|---|
| **mtime** | Unix 纳秒时间戳 | Windows 100ns 精度 / Unix 1ns | 尽力还原，精度损失可接受 |
| **ctime / birthtime** | 同上 | Linux 无法设置 ctime | Windows/macOS 还原，Linux 跳过并报告 |
| **atime** | 同上 | 多数系统挂载时 `noatime` | 尽力，不报告 |
| **POSIX 权限位** | u32 | Windows 无对应概念 | Windows 跳过并报告 |
| **owner / group** | uid/gid + 名称 | 跨机器 uid 无意义 | 默认**不还原**（需 root），仅记录 |
| **符号链接** | 目标路径 | Windows 需管理员权限或开发者模式 | 失败时降级为文本文件 + 报告 |
| **硬链接** | inode 分组 | 需先识别同 inode 的文件 | 尽力，失败则复制成独立文件 |
| **扩展属性 xattr** | key-value | Linux/macOS 语义不同，Windows 是 ADS | 同平台还原，跨平台报告 |
| **macOS resource fork** | 作为 xattr | 仅 macOS | 同上 |
| **空目录** | 索引显式记录 | 无 | 必须还原 |
| **文件名特殊字符** | UTF-8 原样 | Windows 禁止 `\ / : * ? " < > \|`，且禁止 `CON`/`PRN` 等保留名 | 见 §4.3 |

### 4.3 文件名兼容性处理

解压到 Windows 时遇到非法文件名：

```
方案：字符替换 + 冲突检测 + 明确报告

原名：report:2026?.txt
落盘：report_2026_.txt
索引：记录原名，UI 中仍显示 report:2026?.txt
报告：⚠️ 2 个文件名因 Windows 限制被调整
```

**绝不静默丢弃或覆盖**。若替换后产生冲突，追加 `~1`、`~2` 后缀。

### 4.4 还原报告

解压完成后，若有任何元数据无法还原，**必须**显示报告：

```
✅ 解压完成：1,247 个文件，3.2 GB

⚠️ 部分元数据未能还原（当前平台限制）：
   • 1,247 个文件的 POSIX 权限位  —— Windows 不支持
   • 3 个符号链接已降级为文本文件 —— 需要管理员权限
   • 12 个文件名包含非法字符，已调整   [查看详情]

   完整元数据仍保存在加密文件中，在 Linux/macOS 上解压可完整还原。
```

## 5. 原文件处理（决策 D-15：做成选项）

### 5.1 三个选项

```
加密完成后，对原文件：
  ◉ 保留原文件（推荐）
  ○ 移到回收站
  ○ 直接删除
     ☐ 删除前二次确认

  ℹ️ 关于"安全擦除"
     本应用不提供安全擦除功能。在 SSD 上，由于 wear leveling
     和 TRIM 机制，覆写擦除无法保证彻底清除数据。
     如需更高保障，请对整个磁盘使用全盘加密。
```

### 5.2 为什么不提供"安全擦除"

（威胁模型 N8）**提供一个不可靠的安全功能，比不提供更危险**——用户会误以为数据真的被抹掉了。

诚实的做法：明确告知局限 + 推荐真正有效的方案（全盘加密）。

### 5.3 删除前的强制校验

**删除原文件前必须**：
1. 加密文件已完整写入并 fsync
2. 重新读取加密文件并**完整解密一遍**
3. 校验解密结果的 BLAKE2b-256 与原文件一致
4. 校验通过才删除

这一步不能省——否则可能出现"加密文件损坏 + 原文件已删除"的双重丢失。

## 6. 分片

### 6.1 分片参数（决策 D-18）

**手动指定大小**，同时提供常用预设：

| 预设 | 大小 | 用途 |
|---|---|---|
| FAT32 兼容 | 4 GB − 1 B (4,294,967,295) | U 盘、SD 卡 |
| 光盘 | 700 MB / 4.7 GB / 25 GB | 刻录归档 |
| 邮件附件 | 20 MB / 50 MB | 邮件发送 |
| 自定义 | 用户输入 | — |

### 6.2 冗余 header（决策 D-18：要）

`shard_index > 0` 的分片携带完整主 header 副本。

| 收益 | 代价 |
|---|---|
| 任意一片可独立识别文件身份 | 每片增加 `header_len` 字节 |
| 第 0 片丢失后仍能显示文件名和缩略图 | 典型 656 B – 20 KB（取决于是否含缩略图） |
| 每片都带 moov 缓存 → 缺片时仍可播放 | |

**开销估算**：10 GB 文件切成 4 GB 分片（3 片）+ 含 16 KB 缩略图的 header → 额外 32 KB，占比 0.0003%。**完全值得。**

### 6.3 命名与识别

```
movie.mkv.omy.001
movie.mkv.omy.002
movie.mkv.omy.003
```

但**不依赖文件名识别**——归属判定完全基于分片头中的 `file_uuid`。用户改名、乱序、混在一堆文件里都能正确重组。

已验证：随机打乱顺序后 `unshard()` 仍能正确合并。

### 6.4 合并与校验

| 检查 | 失败时 |
|---|---|
| magic 校验 | 报"不是分片文件" |
| `file_uuid` 一致性 | 报"分片属于不同文件" |
| CRC-32 逐片校验 | 报"第 N 片损坏" |
| 序号完整性 | 报"缺少第 [1, 3] 片" |

已验证：缺片能精确报出缺失编号；单字节损坏被 CRC 检出。

### 6.5 缺片时的降级播放（决策 D-18：可选设置）

**可行性来源**：分块 AEAD 的每块独立解密，缺片只影响该片覆盖的字节区间。

```
设置：☑ 缺少分片时，仍尝试播放可用部分

实现：
  1. 建立"空洞表"：记录缺失的字节区间
  2. Range 请求完全落在空洞内 → 返回 416
  3. Range 请求部分重叠 → 返回可用部分
  4. 播放器会跳过无法读取的区间
  5. UI 显示进度条上的缺失区段（灰色）
```

**UI 呈现**：

```
⚠️ 缺少 2 个分片（第 3、5 片），部分内容不可播放

进度条：████████░░░░████████░░░░████
                ↑缺失        ↑缺失
```

⚠️ **关键限制**：若缺失的片恰好包含 MP4 的 `moov` box，整个文件无法播放。

**这正是 `TLV_MOOV_CACHE` + 冗余 header 的第二个价值**——moov 存在 header 里，每片冗余 header 都带一份，所以只要**任意一片存在**，moov 就可用。

### 6.6 分片的原子写入

全部分片写完后再统一 rename，避免"部分分片已就位"的中间态：

```
1. 写 tmp.001, tmp.002, tmp.003
2. 逐个 fsync
3. fsync 父目录
4. 依次 rename → .001, .002, .003
5. fsync 父目录
```

若中途失败，清理所有 tmp 文件。

## 7. 扫描与索引

### 7.1 扫描流程

```
对授权目录中的每个文件：
  1. 读前 8 字节 → 比对 magic
     ├─ 匹配 OMYFILE → 是 .omy 主文件
     ├─ 匹配 OMYSHRD → 是分片
     └─ 都不匹配 → 检查是否伪装文件（读 footer 或宿主扩展区）
  2. 读完整 header
  3. 对每个已解锁的 KEK × 每个 slot 尝试解包（微秒级）
  4. 命中 → 解密 TLV，得到文件名、缩略图、媒体信息
  5. 未命中 → 标记为"已加密，但当前密码无法打开"
```

### 7.2 性能

已验证：500 文件 × 5 密码 = 171 ms，推算 10,000 文件约 3.4 s。

**优化**：
- 只读文件头部（典型 656 B – 20 KB），不读载荷
- 并行扫描（rayon），但注意移动端要限制并发数
- 增量扫描：只处理 mtime 变化的文件

### 7.3 缓存策略（决策 D-19：放内存）

```rust
struct ScanCache {
    // key: (设备号, inode) 或 Windows 的 file_id
    entries: HashMap<FileKey, CachedEntry>,
}

struct CachedEntry {
    mtime: SystemTime,
    size: u64,
    header_len: u32,
    file_uuid: [u8; 16],
    // 解密后的元数据（会话内有效）
    filename: Option<Zeroizing<String>>,
    thumbnail: Option<Zeroizing<Vec<u8>>>,
    media_meta: Option<MediaMeta>,
}
```

**内存缓存的好处**（相比落盘数据库）：
- ✅ 不产生"存着明文文件名的磁盘文件"这个新的泄露面
- ✅ 无需处理缓存与实际文件的一致性问题
- ✅ 会话锁定时随内存一起清零

**代价**：每次启动需重新扫描。10,000 文件 3.4 s 可接受。

**失效条件**：mtime 或 size 变化 → 重新读取该文件。

### 7.4 分片在扫描中的处理

```
扫描到 OMYSHRD magic
  → 读分片头，提取 file_uuid、shard_index、shard_total
  → 按 file_uuid 分组
  → 组内齐全 → 显示为一个完整文件（虚拟合并）
  → 组内缺片 → 显示"⚠️ 3/5 片" + 缺失编号
  → 从任一片的冗余 header 读取文件名和缩略图
```

**UI 中分片集合显示为单个条目**，不暴露物理分片细节（除非用户展开查看）。

## 8. 元数据归一化（决策 D-20：默认关闭）

作为高级选项提供：

| 选项 | 作用 | 代价 |
|---|---|---|
| **抹平时间戳** | 所有加密文件的 mtime 设为固定值 | 云盘同步可能反复触发；原始 mtime 仍存在加密索引中可还原 |
| **大小填充** | 载荷尾部追加随机字节，填充到 2 的幂或固定桶 | 存储浪费最高 100% |
| **诱饵文件** | 生成随机的假 .omy 文件 | 占用空间；扫描时会显示"无法打开" |

**默认全部关闭**，因为威胁模型（N6）不要求隐藏元数据，而代价明显。

`FLAG_META_NORMALIZED` 和 `FLAG_SIZE_PADDED` 用于标记，`SIZE_PADDED` 时真实长度以 `plaintext_size` 为准。
