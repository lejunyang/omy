# 03 · 密钥体系

## 1. 全景图

```
┌─ 用户凭据（四选一或多选）────────────────────────────────────┐
│                                                              │
│  密码           恢复码          生物识别        密钥文件      │
│    │              │                │               │         │
│    ▼              ▼                ▼               ▼         │
│ Argon2id      直接使用        OS 密钥库        Argon2id      │
│ (~180ms)     (熵已足够)      (指纹/面容)      (文件内容)     │
│    │              │                │               │         │
│    └──────────────┴────────────────┴───────────────┘         │
│                          │                                   │
│                          ▼                                   │
│                    KEK (32 bytes)  ◀── 会话内缓存             │
└──────────────────────────┬───────────────────────────────────┘
                           │
        ┌──────────────────┴──────────────────┐
        │  HKDF-SHA256(KEK, file_uuid, info)  │  ~13 µs / 次
        │  每个文件、每个 slot 各派生一次       │
        └──────────────────┬──────────────────┘
                           ▼
                  slot 包裹密钥 (32 bytes)
                           │
                           ▼  AEAD 解包 slot
                    ┌─────────────┐
                    │  FEK (32B)  │  每文件独立随机
                    └──────┬──────┘
                           │
      ┌────────────┬───────┴───────┬─────────────┐
      ▼            ▼               ▼             ▼
  payload_key  header_mac_key   tlv_key[T]   (未来扩展)
  载荷加密      头部完整性       元数据加密
```

**核心思想**：慢速 KDF 只在"密码 → KEK"这一步执行一次；"KEK → 每个文件"用快速 HKDF。

---

## 2. 为什么必须是两级

### 2.1 问题：自动扫描 × 内存硬 KDF = 灾难

需求 F-12 要求扫描授权目录、自动匹配密码。若每个文件用独立 salt 跑 Argon2id：

```
10000 文件 × 5 密码 × 180 ms = 2.5 小时
```

移动端更糟：Argon2id m=64 MiB 意味着**真实分配 64 MiB 内存**，并发几个就会被系统 OOM Killer 杀掉。

### 2.2 曾考虑并否决的方案：kek_id 前缀比对

**方案**：header 存 `kek_id = HKDF(KEK, "id")[0..8]`，扫描时先比对 8 字节，命中才解包。

**否决理由**：相同 `kek_id` 会暴露"这些文件属于同一密码"，破坏可否认性。而且——**它并不比两级 KDF 更快**。

### 2.3 采用方案：两级 KDF

| 方案 | 10000 文件 × 5 密码 | 是否泄露密码关联 |
|---|---:|---|
| 每文件独立 Argon2 | ~2.5 小时 | 否 |
| kek_id 前缀比对 | ~1 s | ⚠️ **是** |
| **两级 KDF（本设计）** | **~3.4 s** | **否** |

两级 KDF 在两个维度上都不输，`kek_id` 方案作废。

### 2.4 实测数据

> 测试环境：容器化 Linux x86-64，Python 参考实现。Rust 实现应更快。

| 操作 | 耗时 |
|---|---|
| Argon2id (m=64 MiB, t=3, p=1) | **180 ms** |
| HKDF-SHA256 | **13.2 µs** |
| 比值 | **13,700×** |

| 场景 | 实测 |
|---|---|
| 5 个密码派生 KEK | 765 ms（每会话一次，缓存复用） |
| 扫描 500 文件 × 5 密码 | **171 ms**（500/500 命中） |
| 推算 10000 文件 | **~3.4 s** |
| 对照：每文件 Argon2 | 450 s（慢 2,627×） |

已验证：非本 vault 的文件不会误命中。

## 3. KDF 参数档位

### 3.1 档位表

| 档位 | m (KiB) | t | p | 桌面耗时 | 适用 |
|---|---:|---:|---:|---|---|
| `mobile` | 32,768 (32 MiB) | 4 | 1 | ~120 ms | 移动端默认 |
| `interactive` | 65,536 (64 MiB) | 3 | 1 | ~180 ms | **桌面默认**（OWASP 基线） |
| `moderate` | 262,144 (256 MiB) | 4 | 1 | ~900 ms | 高价值数据 |
| `sensitive` | 1,048,576 (1 GiB) | 4 | 1 | ~4 s | 长期归档 |
| `custom` | 用户指定 | | | | 高级选项 |

参数含义：
- **`m`（内存成本）**：主要防线。GPU 破解时每个并行实例都要独占这么多显存，把爆破成本拉高 1–2 个数量级
- **`t`（迭代次数）**：线性增加 CPU 时间
- **`p`（并行度）**：lane 数量

### 3.2 移动端保护

⚠️ **`sensitive` 档在手机上会被系统杀掉**（1 GiB 分配）。必须：

1. **写入时**：移动端 UI 默认只提供 `mobile` / `interactive`，更高档位需明确警告
2. **读取时**：读到 header 中的参数发现超出本机能力 → **给出明确提示**，而非崩溃
   ```
   ⚠️ 此文件使用了高强度加密参数（需 1 GiB 内存）
      当前设备可用内存不足，请在桌面端打开
   ```
3. 实现上：解锁前先查询可用内存，预留安全边界

### 3.3 参数存储

Argon2 参数**存在每个文件的 header**（偏移 56–67），且被 header MAC 覆盖。

- ✅ 换设备、换版本后仍可解开
- ✅ 攻击者无法篡改参数做降级攻击（威胁 T7，已验证检出）

## 4. Key Slot 体系

### 4.1 四种 slot 类型

| 类型 | KEK 来源 | 扫描时尝试 | 用途 |
|---|---|:---:|---|
| **vault** | `Argon2id(密码, vault_salt)` | ✅ | 日常使用，KEK 会话内缓存 |
| **device** | OS 密钥库解包出的设备密钥 | ✅ | 生物识别 |
| **portable** | `Argon2id(密码, 文件独立 salt)` | ❌ | 单独分享出去的文件 |
| **recovery** | 恢复码直接作为 KEK | ❌ | 灾难恢复 |

**为什么 portable / recovery 不参与扫描**：它们需要独立跑 Argon2 或用户手动输入，成本高。只在用户**手动打开单个文件**时尝试（几百毫秒可接受）。

一个文件可同时挂多种 slot。典型配置：

```
slot[0] = vault    (主密码)
slot[1] = device   (本机指纹)
slot[2] = recovery (恢复码)
slot[3..7] = 随机填充
```

### 4.2 单文件带走的场景

vault slot 依赖 `vault_salt`，而 `vault_salt` 存在文件 header 里 —— 所以**文件拷到任何机器都能解开**，只要知道密码。

那 portable slot 的意义是什么？**给不同的密码**。场景：

> 你想把某个加密文件发给同事，但不想告诉他你的 vault 主密码。
> → 给这个文件加一个 portable slot，用一次性密码 `temp-2026`。
> → 同事只能打开这一个文件，无法打开你其他任何文件。

### 4.3 slot 管理操作

| 操作 | 实现 | 成本 |
|---|---|---|
| 添加密码 | 新增一个 slot，重新包裹同一个 FEK | 毫秒级（不重新加密载荷） |
| 删除密码 | 该 slot 覆写为随机字节 | 毫秒级 |
| 修改密码 | 删旧 slot + 加新 slot | 毫秒级 |
| 轮换 FEK | 必须重新加密整个载荷 | 与文件大小成正比 |

⚠️ **删除 slot 的局限**：如果攻击者已经保留了旧版本文件副本，删除 slot 无法阻止他用旧密码打开旧副本。**真正的密钥轮换需要重新加密**（UI 应提供"重新加密"选项并说明差异）。

## 5. 可否认性

### 5.1 实现机制

三个要素共同作用：

1. **固定 8 个 slot**，无论实际用了几个
2. **未使用的 slot 填充密码学随机字节**
3. **同一 vault 的多个密码共用 `vault_salt`**

结果：

```
Argon2id(密码甲, vault_salt) → KEK甲 → 打开文件集 A（真实文件）
Argon2id(密码乙, vault_salt) → KEK乙 → 打开文件集 B（诱饵文件）
```

外部观察者看到的所有文件**长得一模一样**，无法判断：
- 某个文件有几个真实密码
- 是否存在"另一个密码"
- 哪些文件属于哪个密码集

### 5.2 验证结果

| 检验 | 结果 |
|---|---|
| 1 密码 vs 3 密码的文件大小 | 772 B vs 772 B ✅ |
| 1 密码 vs 3 密码的 header_len | 相同 ✅ |
| slot 区香农熵 | 7.491 bits/byte，落在纯随机基线 [7.332, 7.508] ✅ |
| 真实 slot 段 vs 填充段熵差 | 0.506 < 随机对照组 p95 (0.597) ✅ |
| 同密码不同文件的 slot 内容 | 完全不同 ✅（因 `file_uuid` 不同） |

### 5.3 ⚠️ 可否认性的真实边界

**必须诚实告知用户**（威胁模型 N5）：

| 能挡住 | 挡不住 |
|---|---|
| 从文件本身推断存在几个密码 | 持续的物理胁迫 |
| 从文件大小/结构推断隐藏内容 | 你的使用习惯（最近打开记录、文件数量异常） |
| 静态分析发现诱饵密码集 | 对方知道本软件"固定 8 槽"的设计（开源，规范公开） |

**关键局限**：因为本项目开源、格式公开，任何人都知道"CryptoVault 文件恒有 8 个 slot"。所以可否认性**不是"证明不存在其他密码"，而是"无法证明存在"**。这在法律和胁迫场景下的实际价值有限。

**给用户的建议文案**（UI 中展示）：
> 可否认性可以让别人无法从文件本身判断你是否还有其他密码。
> 但它不能对抗持续的胁迫，也不能掩盖你的使用痕迹。
> 请不要把它当作生命安全的保障。

## 6. 文件伪装

用户要求两种识别方式都支持（决策 D-17），需说明差异。

### 6.1 方式 A：Footer Magic

```
┌─────────────────────────────┐
│  宿主格式头（合法 JPEG/PNG） │  ← 双击可用系统看图软件打开
├─────────────────────────────┤
│  真实 .cvlt 数据             │
├─────────────────────────────┤
│  footer: magic + u64 偏移    │  ← 文件末尾 16 字节
└─────────────────────────────┘
```

| 优点 | 缺点 |
|---|---|
| 实现简单，适用任何宿主格式 | 需要读文件末尾（网络场景多一次请求） |
| 宿主内容可以是任意有效文件 | 某些严格的解析器会报"文件尾部有多余数据" |

### 6.2 方式 B：宿主格式扩展区

把真实数据塞进宿主格式的**合法扩展区**：

| 宿主 | 扩展区 |
|---|---|
| JPEG | `APPn` segment（APP4–APP15 通常空闲） |
| PNG | 私有 chunk（小写首字母 = ancillary，解析器会忽略） |
| MP4 | `free` / `skip` box |
| PDF | 对象流 |

| 优点 | 缺点 |
|---|---|
| 宿主文件**完全合法**，严格解析器也不报错 | 每种宿主格式要单独实现 |
| 只需读文件头部即可定位 | JPEG APPn 单段上限 64 KB，大文件需分段 |

### 6.3 对比与建议

| | 方式 A（Footer） | 方式 B（扩展区） |
|---|---|---|
| 实现复杂度 | 🟢 低 | 🟡 中–高 |
| 宿主格式合法性 | 🟡 尾部有多余数据 | 🟢 完全合法 |
| 定位成本 | 需读尾部 | 只读头部 |
| 大文件支持 | 🟢 无限制 | 🟡 JPEG 需分段 |
| **推荐场景** | 默认选择 | 需要通过严格校验时 |

### 6.4 ⚠️ 伪装的真实强度

**必须在 UI 明确告知**：

> 伪装模式可以让文件在文件管理器里看起来像一张普通图片，双击也能正常打开。
> **但这只能挡住随手点开的人。** `binwalk`、`file`、任何十六进制编辑器都能一眼看穿。
> 这不是隐藏卷，不要用它对抗专业检查。

## 7. 生物识别

### 7.1 一个必须纠正的误解

**生物识别本身不产生密钥。** 指纹/面容是**门禁**，不是**钥匙**：

```
指纹/面容 ──解锁──▶ OS 密钥库中的设备密钥 ──解包──▶ KEK ──▶ FEK
```

真正的密钥始终由操作系统的安全硬件保管。

### 7.2 各平台实现

| 平台 | 密钥库 | 硬件后端 | 关键 API |
|---|---|---|---|
| **Android** | Android Keystore | TEE / StrongBox | `setUserAuthenticationRequired(true)` |
| **iOS** | Keychain | Secure Enclave | `kSecAccessControlBiometryCurrentSet` |
| **Windows** | Windows Hello + DPAPI-NG | TPM | `KeyCredentialManager` |
| **macOS** | Keychain | Secure Enclave (T2/M 系列) | `SecAccessControlCreateWithFlags` |
| **Linux** | 无统一方案 | — | 降级为 Secret Service / 不支持 |

### 7.3 三条硬性约束

1. **必须永远保留密码 slot 作为后备**

   device slot 会在以下情况失效：
   - 换设备
   - 重装系统
   - 重新录入指纹/面容
   - **Android：修改锁屏密码会直接使 `setUserAuthenticationRequired` 的 key 失效**
   - iOS：`BiometryCurrentSet` 在生物特征变更时主动失效

   → UI 必须在启用生物识别时强制提示"密码仍是唯一可靠的解锁方式"

2. **device slot 是便利性，不是恢复手段**

   它绑定单台设备，不能跨设备迁移，不能当备份。

3. **需要自研原生插件**

   Tauri 的 biometric 插件能力有限，`StrongBox`、`setUserAuthenticationValidityDurationSeconds`、`BiometryCurrentSet` 这些细粒度控制需要自己写 Kotlin/Swift。

### 7.4 KEK 的存储方式

```
生成随机 device_key (32B)
  → 存入 OS 密钥库，标记"需生物识别才能读取"
  → wrapped_kek = AEAD(device_key, KEK)
  → wrapped_kek 存入应用配置（非密钥库，因为它已被保护）

解锁时：
  生物识别 → OS 返回 device_key → 解出 KEK → 缓存到会话
```

## 8. 恢复方案

因为是两层密钥，**所有恢复手段本质上都只是"多加一个 slot"**，不需要重新加密任何文件数据。

### 8.1 六种方案对比

| 方案 | 机制 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **A. 恢复码** | 256-bit 随机 → 24 词助记词。熵足够，**无需 KDF**，直接作 KEK | 简单、离线、跨设备 | 纸质件丢失即失效；**拿到即全权访问** | ⭐ **默认引导** |
| **B. Shamir 秘密共享** | 拆成 n 份，任 k 份可还原（如 3-of-5） | 抗单点丢失 + 抗单点泄露 | 管理复杂，普通用户易搞丢 | 高级选项 |
| **C. 密钥文件** | U 盘上的文件作为 slot，或与密码组成双因子 | 易用、可物理隔离 | U 盘会坏、会丢 | 高级选项 |
| **D. 生物识别** | 见 §7 | 日常最方便 | **设备绑定，不是恢复手段** | 便利功能 |
| **E. 非对称托管** | 内置 X25519 公钥 slot，私钥离线保存 | 日常无需接触私钥；适合长期归档 | 私钥泄露 = 全库沦陷 | 高级选项 |
| **F. 不做恢复** | 明确告知"忘密码 = 永久丢失" | 最安全、最诚实 | 用户体验差 | 可选关闭 |

### 8.2 恢复码格式

```
24 词 BIP-39 风格助记词（256 bit 熵 + 8 bit 校验）：
  abandon ability able about above absent absorb abstract
  absurd abuse access accident account accuse achieve acid
  acoustic acquire across act action actor actress actual

或分组编码（便于手抄）：
  CVLT-A3F9-2B71-8E4D-...-XK92    （含 CRC 校验位）
```

**为什么不需要 Argon2**：256 bit 随机熵已远超任何密码，暴力破解不可行。直接用 HKDF 派生即可。

### 8.3 ⚠️ 必须写进 UI 的两条警告

1. **每多一个 slot 就多一条攻击路径。** 恢复码的强度就是整个 vault 的强度下限——它是一张明文纸条。

2. **恢复码与可否认性冲突。** 虽然固定 slot 数掩盖了数量，但如果你把恢复码打印出来放在家里，胁迫场景下它就是突破口。

## 9. 密码强度策略

### 9.1 设计原则

**警告但不强制。** 开源工具不应家长式管控用户。

### 9.2 实现

1. 接入 **zxcvbn** 做强度评估（0–4 分）
2. 低于阈值时显示警告，但允许继续
3. **显示可理解的破解成本估算**：

```
┌────────────────────────────────────────────┐
│ 密码强度：⚠️ 弱 (2/4)                       │
│                                            │
│ 以当前参数 (Argon2id m=64MiB, t=3)：        │
│   单张 RTX 4090 约需  3 天                  │
│   1000 张 GPU 集群约需 4 小时               │
│                                            │
│ 提升到 4/4 强度后：                         │
│   1000 张 GPU 集群约需 8000 年              │
└────────────────────────────────────────────┘
```

⚠️ 估算必须标注"仅供参考，实际取决于攻击者算力和密码是否在字典中"。

### 9.3 弱密码 + 弱参数的组合风险

用户可以同时选择弱密码和低 Argon2 参数，这会让整个设计形同虚设。UI 应在这种组合下给出**联合警告**。

## 10. 内存卫生

威胁模型排除了内存取证（N2/N3），但低成本的措施仍应做：

| 措施 | 是否实施 | 理由 |
|---|---|---|
| `zeroize` 清除密钥 | ✅ 必做 | 成本极低，Rust 有成熟 crate |
| 密钥类型用 `Zeroizing<T>` 包装 | ✅ 必做 | 编译期保证 Drop 时清零 |
| `mlock` 防换页 | ❌ 不做 | 威胁模型不要求；跨平台行为不一致；有权限问题 |
| 前端 WebView 中不出现密钥 | ✅ **必做** | 见下 |
| 大块明文不走 IPC | ✅ **必做** | 见下 |

### 10.1 前端隔离（重要）

**密钥绝对不能进入 WebView 的 JS 环境。**

```
❌ 错误：invoke('get_fek') → JS 拿到密钥 → JS 解密
✅ 正确：JS 只持有不透明的 file_id
         <video src="cvault://file/{file_id}">
         Rust 侧在自定义协议 handler 内完成解密
```

同理，**大块明文也不走 IPC**：走自定义协议流式返回，字节从 Rust 直接进入媒体管线，不经过 JS 堆。

⚠️ 例外：MSE 路径（P2/P3）下解密后的数据**必须**经过 JS `appendBuffer`。这是该路径固有的攻击面扩大，在本威胁模型下可接受，但应在文档中标注。

## 11. 会话与锁定

### 11.1 KEK 缓存

```
缓存键：(vault_salt, 凭据标识)
缓存值：KEK (Zeroizing<[u8; 32]>)
生命周期：会话内
```

### 11.2 自动锁定触发条件

| 条件 | 默认 | 可配置 |
|---|---|---|
| 空闲超时 | 15 分钟 | ✅ |
| 系统睡眠/锁屏 | 立即锁定 | ✅ |
| 应用切后台（移动端） | 立即锁定 | ✅ |
| 手动锁定 | — | 快捷键 |

锁定时：清零所有 KEK 和 FEK 缓存、关闭所有打开的媒体流、清理 WebView 缓存。

### 11.3 移动端任务切换器截图

iOS/Android 在应用切后台时会截屏用于任务切换器，**可能泄露已解密的内容**。

对策：
- iOS：`applicationWillResignActive` 时覆盖一层模糊视图
- Android：`FLAG_SECURE` 禁止截屏（同时也阻止用户主动截屏，需做成可配置）
